# 連鎖佇列開了沒人跟完

**一句話**：`decision-supersede` 會自動幫你開一張「誰引用了這條被推翻的決策」的待辦單，**但沒有任何東西會提醒你那張單還沒做**——歷來開過兩張，兩張都是空的。

## 現況（2026-08-13 實測）

```
$ lumos rel-cascade list
c-20260804063546-eb0fe2fc  root=Projects/design-loop重設計.md#d3                  confirmed=0 pruned=0
c-20260811044607-50e3a09c  root=Projects/Android側UI測試綁架構圖工作流_計劃.md#d2   confirmed=0 pruned=0
```

兩張帳本都只有 `header` 一筆事件，沒有任何 `confirm`／`prune`。**第二張是本人 2026-08-11 在 Android UI design-loop r2 翻盤 d2 時開的**——當下我完全不知道有這張單存在，直到今天為了別的事去查 `governance/rel-cascade/` 才看到。

★這不是紀律問題，是路徑問題★：`rel-cascade list` 要**主動跑**才看得到；`doctor` 不報、`pre-push` 不提、supersede 當下的輸出也沒說「接下來請跑 rel-cascade」。

## 同一病灶的另一面：已死節點仍被引用

| 狀態 | 被引用 | 節點 |
|---|---|---|
| superseded | **5** | `2026-08-03_Windows真機驗證五缺陷修復` |
| stale | 2 | `2026-07-10_guard殺傷力驗證` |
| superseded | 1 | `mutate接消費者_計劃` |
| rejected | 1 | `judge-perturbation-stability` |
| deferred | 1 | `core-invariant-baseline` |

10 處引用，**沒有一處承認來源已失效**。源頭標了記號，下游沒人回去問「那我的結論還站得住嗎」。

## 為什麼現在提（觸發來源）

2026-08-13 治理日報的【對抗】缺口：「架構圖預設知識存越多越好，外部卻量到池子過大反而變差」，引 arXiv 2608.05810（*When Self-Evolution Backfires*）——**壞的一旦被引用衍生，事後刪源頭救不回**。

順著那條去量自家架構圖（269 篇／156 萬字元／48 天／增速 4-5 篇/天），結論**不是**「節點太多」：
- 84%（227 篇）是 `done`／`pass` 的**死存檔**，不會被蒸餾成新結論，成本近乎零
- 真正對應論文「技能池」的活池 ≈ **80 篇**（Systems 53 ＋ 活 Projects/Issues）
- 我們的檢索是 ranked top-N，不是全讀 → 失效形狀是「相關的排不進去」（真遺忘），不是「讀太多變差」

★所以該收的不是節點數，是**衍生污染**★——而衍生污染的機制我們**已經有**，只是沒在跑。

**本 repo 三天內的三個衍生實例**（都靠人／panel 撈回，沒有機制）：
1. 「19 條 kotlin 綁定」（實為 5）被寫進 spec 後，**被三處引用**當驗收判準 → r2 兩席各自實跑才抓回
2. delguard 歸因錯被寫進審計修正紀錄，成為「這型失守已有守衛」的依據 → 三席一致抓回
3. Verification 的測試數字快照**兩度過期**

## PRIOR-ART

- **① 最小解在哪一層**：`rel-cascade` 帳本／CLI／`backlinks`／`doctor` 的 soft check 機制**全部現成**——缺的只是「有未完成連鎖時出聲」。不造新機制、不新增治理層。
- **② 世界解過沒（真搜）**：學術界的撤稿傳播是同一題且量測充分——撤稿後仍被引用是常態，**撤稿後的引用只有 5.4% 承認撤稿**；且傳播**主要靠直接引用**而非間接（[Continued use of retracted papers](https://www.ncbi.nlm.nih.gov/pmc/articles/PMC9520488/)、[Propagation of errors in citation networks](https://www.ncbi.nlm.nih.gov/pmc/articles/PMC5793988/)、[On the shoulders of fallen giants](https://direct.mit.edu/qss/article/5/1/1/120306/On-the-shoulders-of-fallen-giants-What-do)）。★「主要靠直接引用」直接支持既有裁定★：連鎖用「確認才前進的工作清單」、不盲展 N 跳。
- **③ 裁定＝borrow-design**：借「撤稿通知要推到直接引用者」的意圖，原生實作（掛既有帳本），零依賴家規排除 adopt。

## 新機制準入三問（Growth test）

1. **真造成過事故嗎**：是——2/2 連鎖零處理、10 處引用已死節點無人回問、三天內三個衍生實例。不是「感覺會出事」。
2. **是風格偏好嗎**：不是，是「開了單沒人做」的可數事實。
3. **既有機制小修蓋得住嗎**：**蓋得住**——這正是本 Issue 的主張。故不開新計劃節點。

- [ ] **C · 把現有兩張欠帳跟完**：`c-20260804063546`（design-loop重設計#d3）與 `c-20260811044607`（Android UI #d2）——★這兩張同時是 B 的首發驗收樣本★（8/13 日報 inspirations：「每支新檢查上線時附一組『一定要被它抓到』的樣本」）
- [ ] **D（另議，較大）· 已死節點的引用面**：上表 10 處引用要不要也納入同一條軟提醒，或歸 `doctor Check E` 擴充

## 天花板（先寫明）

- A／B 都是**軟提醒，不是閘**——忘了還是會忘，只是從「完全沒訊號」變成「有訊號」。
- 只管**直接引用**一層（外部證據支持這樣就抓到大部分，但**不是全部**）。
- 這條**不解決**「壞結論還沒被標成失效」的情況——它只在有人 supersede 之後才啟動；沒人發現錯的那些，仍歸 AI 交叉審與 CheckY／CheckN／CheckU。
