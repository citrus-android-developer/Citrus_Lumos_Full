# 量測快照過期無守衛

## 問題

Verification 節點裡的**實跑量測值**——`_delguard_confidence 159.97s`、`10 個常見 token 83.71s`、`完整掃描逾 5 分鐘未完成`——在修法把它們改掉之後，原文仍原樣留著。

架構圖沒有任何機制知道這些數字已經不代表現況。目前全靠人在修完之後**回頭手動**去每一篇補一句「這是歷史值」。

## 為什麼這比一般的過期敘述危險

一般的過期敘述（「某功能未實作」）讀者還能靠常識起疑。**數字不會**——`83.71s` 看起來就是個事實，沒有任何地方寫著它綁定哪個版本。

而 `lumos search` 的行為正好放大這點：命中片段常常落在正文中段的量測表格附近，而追記警語（節點開頭的 `⚠` 橫幅或文末的殘項段）看不到。讀者拿到的是一個「看起來有憑有據的數字」加上零過期訊號。

## 實證

2026-08-27 對 delguard 那條線做自足性審計時，第二輪的乾淨 agent 主動把這點列為本次審計**最容易踩的坑**，原話是：「看到 delguard 的秒數，一定要往下讀到節點末尾確認有沒有追記覆蓋」。

那一輪之所以沒踩，是因為前一天的兩篇節點剛好在同一天被手動補上了「⚠ 重驗觸發已成立」橫幅——★靠的是人記得補，不是機制★。

## 為什麼不能直接套 Check N

[[Systems/check-n-recomputable]] 守的是**可重算**的宣稱：計數、行號，用 `lumos:count` 標記存查詢不存答案，doctor 用 re + glob 重掃 repo 算實際值再比對。

量測快照**結構上不可重算**。它綁定的是當時的機器、系統負載、資料規模、被測程式版本；重跑一次只會得到另一個快照，不是「正確答案」。所以 Check N 那套「存查詢不存答案」的形狀套不上來，需要另想。

## 候選解

見 summary 四條。核心分歧是**治根因（讓 doctor 能判斷量測值是否過期）還是治呈現（讓過期的數字一眼看得出來）**——前者要動檢查面且要決定「被測版本」怎麼記，後者便宜但只降低誤讀機率、不消除。
