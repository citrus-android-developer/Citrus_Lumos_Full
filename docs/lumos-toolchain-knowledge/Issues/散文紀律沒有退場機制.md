# 散文紀律沒有退場機制

## 現況（可數事實，2026-08-13 量）

| 載體 | 規模 |
|---|---|
| `CLAUDE.md` | 46 行／3,504 字元 |
| 8 支 `SKILL.md`（`skills/`，不含 dist 與 slim 副本） | 68,105 字元 |
| 3 支 `reference.md` | 74,305 字元（project-notes 一支就 53,948） |
| `skills/` 全樹 `*.md` | 150,810 字元 |

**這裡面被前後量過效果的紀律：0 條。** 查法：`lumos search` 找「前後／對照／量／紀律／效果」與「退役／移除／規則／無效」，命中的節點談的都是**檢索召回**與**canary 判定**的前後對照，沒有一篇在量某條散文紀律本身。

## 真正的破口不是「有沒有想過」，是「沒有出口」

架構圖**不是**沒意識到沉積。[[Projects/skill寫法學借鑒與design-loop剪枝]] 已經收了五個失效模式，其中兩個正對這題：

- **sediment**——「加東西感覺安全、刪東西感覺危險，於是陳舊的層一直堆著。**沒有剪枝紀律的 skill 的預設命運。**」
- **no-op**——「模型本來就會做的事⋯⋯**測試：這句拿掉，行為會不一樣嗎？** 不會就刪整句。」

問題出在同一份節點的硬不變量。剪枝**只准三種操作**：壓縮措辭、搬家去 `reference.md`、刪除純考古（日期出處／工作包編號／論文引用）。並明令：

> **不准**：刪規則、弱化判準、把「必須」改成「建議」。

### ★精確界定：那條不變量的效力範圍★（2026-08-13 二輪審計後更正）

原稿把它當成常設全域規則寫，**不準確**。查證後的實情：

- 那條不變量寫在該節點的 **「## 本次動刀範圍」** 底下（該次只動 `lumos-design-loop` 一支），★是為那一次剪枝作業定的規矩，不是宣告全 repo 常設★。
- ★該節點**沒有**交代這條不變量的立法理由★——只有規定，沒有 why。

所以更精確的處境是：**全 repo 根本沒有任何一條關於「散文紀律怎麼退場」的常設規定**，一條都沒有；我們唯一有過的一次前例，明令禁止刪。

結論不變、理由要換：★不是「有一條惡法擋著」，是「這件事從來沒被立過法，而唯一的前例是禁止」★。一條當初立得合理、後來證明沒用（甚至有反效果）的紀律，實務上沒有出口——它只會被壓得更短、搬得更深，永遠留在載入路徑上。

### ★那份節點自己就自相矛盾★（2026-08-13 自足性審計指出，非本 Issue 原稿發現）

同一份節點的兩段話直接對撞：

| 位置 | 說什麼 |
|---|---|
| 硬不變量段 | **不准刪規則** |
| 五失效模式 · no-op | 「這句拿掉，行為會不一樣嗎？**不會就刪整句**，不要修辭」 |

no-op 判準**字面上就是在刪規則**。所以真正的處境比「沒有尺」更糟：★現在如果有人真拿 no-op 測試去刪一條紀律，架構圖裡沒有任何一處能告訴他這樣算不算違規★。那條判準被記在檢查表裡當「認知」，實際上**結構性動不了**——執行它就等於違反同一份節點的硬不變量。

而 no-op 判準本身還是**讀了之後用判斷力答的**，不是量出來的。判的人正是寫的人，與「design-loop 對散文空轉」是同一形狀：機械核心收斂得動，散文摳不出東西。該裁定的落點見 [[Projects/pitfalls網搜補漏_計劃]]（純散文 skill 直接跳 design-loop 的理由）。

### ★別把「字數變少」當成「規則被驗過」★

[[Projects/skill寫法學借鑒與design-loop剪枝]] 已經跑完一輪並驗收 PASS，但它處理的是**表達效率**，不是**內容有效性**——兩件事掛在「散文紀律」同一個標題下，極易混為一談：

- 它量到的：design-loop 的 SKILL.md 從 15,462 降到 11,053 字元（−28.5%）、最長單行 1,361 → 455；驗收走機械清單 diff（指令名 9→9、旗標 25→25、wikilink 10→10，★零消失★）＋獨立 opus agent 逐條覆核 30 章節，PASS。
- ★它自己記下的天花板★：**剪枝的收益（模型是否更可靠地走同一條路）本身沒有機械量測**，只證明了「規則沒少、字數變少」。而且拆檔有結構成本——兩檔合計字元數反而 **+11%**。

所以本 Issue 要補的不是那一輪的延伸，是**另一個軸**：那 150,810 字元裡，有哪幾條是拿掉之後指標不會變差的。★零條被這樣問過★。

## 為什麼現在提（觸發來源）

2026-08-13 治理日報的第二個【對抗】缺口：「紀律寫進規矩書散文被當成落地，但程序性指示可能有反效果」。

日報的措辭是關鍵——**新證據不是「文字很弱」，是「可能有害」**。

## 外部證據

**① TDAD（arXiv 2603.17973）** 量的是「AI 改完程式，把原本會過的測試弄壞」的比率：

| 做法 | 回歸率 |
|---|---|
| 什麼都不加（基準） | 6.08% |
| 只在指示裡加一段「請照測試先行的程序做」 | ★9.94%★（比什麼都不加**更糟**） |
| 給機械算出的「這次該跑哪些測試」清單 | 1.82% |

**② AGENTS.md 實測（arXiv 2602.11988，ETH Zurich，Gloaguen 等，438 題含 SWE-bench Lite 與自建 AGENTbench）**——這篇量的**就是我們這種檔案**：

- LLM 生成的脈絡檔：成功率 **-3%**、成本 **+20%**
- 開發者手寫的脈絡檔：成功率 **+4%**、成本 **+19%**
- 作者結論：**不必要的需求會讓任務變難，人寫的脈絡檔只該描述最小必要需求**

★兩篇合起來的意思★：把紀律寫成散文塞給模型，最好的情況是花 19% 成本換 4%，最壞的情況是主動把事情弄糟。而我們現在的制度**只允許往上加**。

## PRIOR-ART

- **① 最小解在哪一層**：既有剪枝紀律**已經有** sediment／no-op 的認知與檢查表，缺的只是①一把尺（量過才算判定）②第四種合法操作（量過沒效→撤）。★不造新機制、不新增治理層★。
- **② 世界解過沒（真搜）**：解過，而且工具成熟——**prompt ablation** 是標準做法：逐條移除指示、跑同一組評測、比對指標差異，用來判斷每一段到底有沒有貢獻。上面兩篇是把這套方法直接套在「repo 層脈絡檔」上的實測。相關實務討論（[AGENTS.md bloat](https://codex.danielvaughan.com/2026/03/27/agents-md-bloat-problem/)、[prompt bloat](https://redis.io/blog/prompt-bloat-llm-apps/)）也一致指向「lost in the middle」：規則埋得越深越不被遵守。
- **③ 裁定＝borrow-design**：借 ablation 的**方法**（單條移除 × 固定評測 × 前後對照），原生實作在既有剪枝流程裡。零依賴家規排除 adopt。

## 新機制準入三問（Growth test）

1. **真造成過事故嗎**：★否——這是本 Issue 最弱的一環，要誠實記著★。自家沒有任何一次量測顯示某條散文紀律造成傷害。**有的是**：載體規模可數（15 萬字元）、量過的條數為零、沒有任何退場規定，以及外部對同型載體的直接量測。
   - ⚠ **但「證據缺席」在這題上不是中性的**（二輪審計指出）：自家零實測，★部分正是因為沒有人做過 ablation、也沒有制度要求做★。用「沒證據」當作「不重要」的理由會形成迴圈——沒機制→沒數字→判不重要→不建機制。**這不改變 P2 的判定**（外部數字終究不是自家數字），但它是修法 A 該先跑的另一個理由。
2. **是風格偏好嗎**：不是。「零條被量過」「全 repo 零常設退場規定」「唯一前例明令禁刪」三件都是可查證的事實，不是主觀感受。
3. **既有機制小修蓋得住嗎**：**蓋得住**——就是給剪枝加一把尺與一個出口。故不開新計劃節點。

## 修法（待裁）

- [ ] **A · 先挑一條試打**：選一條可疑的程序性散文紀律，做一次真 ablation：帶／不帶各跑同一組任務，比對一個既有可量指標。★這一條做不出來，B/C 全都不用談★。
  - ★首選標的＝「動任何既有系統之前，第一個工具呼叫必須是 `lumos`」★。理由：它是我們最貴、最常被載入、形狀最標準的程序性指示（「請先做 X 再做 Y」），與 TDAD 打中的「請照測試先行做」完全同型。**選它會不舒服，但正因為不舒服才該先量它**——挑一條無關痛癢的來打，這輪就白做了。
- [ ] **B · 剪枝加第四種合法操作，並順手解掉自相矛盾**：在既有硬不變量下開一道窄門——「**經前後量測顯示無改善或倒退**」的規則准予撤除，且**必須附上那次量測**。沒有量測仍然一律不准刪。（★推測：原不變量的意圖是防止憑感覺砍規則★——**該節點並未寫出立法理由**，這是本 Issue 的揣測，不是原作者的話；若揣測錯了，這道窄門的「不牴觸原意」論證同時失效，要重新談。）★同一次要處置上面那條 no-op 判準★：要嘛把它改寫成「量過沒差才准刪」納入窄門，要嘛承認它與硬不變量衝突並刪掉它——不能繼續兩條並存。
- [ ] **C · 新增紀律時的入場費**：每加一條散文紀律，同時寫明「**它應該改善哪個可量指標**」。寫不出來的，明記為「未量」——不擋，但別讓它享有跟量過的條款同等的地位。
- [ ] **D（另議）· 往機械化搬**：TDAD 的 1.82% 來自機械算好的清單，不是散文。凡是能算出來塞到眼前的（既有的動手前影響提示、共改守衛、測試對照表都屬此類），優先搬過去，而不是在規矩書再寫一句。

## 這條不涵蓋什麼

- **不涵蓋硬護欄**。既有剪枝節點對 negation 只採一半，理由是「lumos 的嚴禁／不得多屬硬護欄」——★那些不在本 Issue 射程內★，本 Issue 談的是**程序性指示**（「請先做 X 再做 Y」）這一型。
- **不涵蓋架構圖節點數**。那題由 [[Issues/連鎖佇列開了沒人跟完]] 處理，且該 Issue 已量過並判定「該收的不是節點數，是衍生污染」。載體不同：架構圖是 ranked top-N 檢索，規矩書是每輪全量載入。
- **★涵蓋「架構圖先行」紀律本身★**（自足性審計追問後補明，2026-08-13）。審計員問了一個原稿避開的問題：這整套「動手前先查架構圖」的紀律，本身正是那兩篇論文量測的那一類程序性脈絡檔——本 Issue 涵不涵蓋它？★答案是涵蓋，而且它是修法 A 的首選標的★。把自家最貴的那條紀律排除在射程外，這張單就退化成只敢打軟柿子的形式主義。
  - ⚠ **「首選待測」≠「已判定有害」**（二輪審計提醒此處易被一眼誤讀）。★架構圖沒有任何一處判定架構圖先行紀律有問題★；它被提名，是因為它形狀最標準、量起來最有資訊量。量完可能證明它很有效——那也是收穫。
- **不涵蓋「規則寫得好不好」**。表達效率那一軸已由 [[Projects/skill寫法學借鑒與design-loop剪枝]] 跑完一輪（壓縮／搬家／機械 diff 驗收）。本 Issue 只問一件事：**這條規則帶著跑，指標會不會比較好**。
