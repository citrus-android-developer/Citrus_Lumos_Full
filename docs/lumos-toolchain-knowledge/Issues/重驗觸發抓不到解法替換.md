# # 重驗觸發抓不到解法替換

## 問題

`revalidate_when` 是 Verification 的必填欄位，語意是「改到什麼程度時該重驗本篇」。實務上作者是**站在當前解法內部**列舉變動軸：調哪個參數、換哪個旗標、升哪個版本、資料規模變到哪。

「這個問題被**另一種方法**整個解掉了」不在任何一條軸上。於是 `lumos stale --match` 掃不到，那篇 Verification 的結論就在已經不成立之後繼續活著。

## 實證（2026-08-27）

[[Verification/2026-08-26_全repo術語統一為架構圖]] 登記了一條 `★DEBT★`：「delguard 預設 deadline 僅 2.0s，大 commit 必定超時 fail-open」。它的 `revalidate_when` 列了兩條：

1. deadline 調整
2. pitfalls 併發規則改版

隔天（8/27）成本問題被解掉了，但**解法是改 grep 形狀**（單次多 `-e` 合併 → 逐 token 各跑一次，見 [[Verification/2026-08-27_delguard逐token-grep]]），deadline 預設值**至今仍是 2.0s、一個字沒動**。

兩條觸發條件一條都沒命中。那條 DEBT 在不成立之後又活了一整天。

## 靠什麼撿回來的

不是機制，是 `lumos-project-notes` 的**退場自問**：這次改動拿掉／反轉了什麼 → 把那些名字逐個丟 `lumos search --code` → 逐句判「改動後這句還成立嗎」。

而且★第一輪還漏了★——當時只搜了「單次 git grep」「合併 grep」這兩個詞，沒搜「掃描成本」，這兩篇因此沒被掃到。是第二輪自足性審計（乾淨 agent 只讀架構圖）才把它們挑出來。**兩次才撿齊，且兩次都靠自律**。

## 為什麼既有守衛結構上抓不到

| 守衛 | 為什麼不響 |
|---|---|
| delguard | 守的是「code 拿掉了某符號、架構圖還在講它」。這型**沒有符號消失**——`_delguard_confidence` 函式名沒變，只有內部實作換了 |
| cochange | 守的是共改關係，跟語意結論無關 |
| impact | branch-range 的影響面提醒，不判某篇結論是否仍成立 |
| `lumos stale --match` | 完全依賴 `revalidate_when` 的字面，而問題正是那些字面列舉不全 |

## 與姊妹 Issue 的關係

與 [[Issues/量測快照過期無守衛]] **同根不同軸**：兩者都是「節點寫下時是對的，世界變了沒人叫醒它」。差別在那篇過期的是**數字**（可以靠標記被測版本來判），本篇過期的是**結論**（「這個問題還沒解」），判斷需要語意，不是比對版本就能知道。可能各自要不同解，不宜綁在一起處理。

## 候選解

見 summary 五條。核心分歧是**要不要承認「條件列舉」這條路本身不可靠**——③的罐頭條款等於明說列舉不全是常態；①②則是繞過列舉，改從「誰作廢了誰」或「時序倒掛」去偵測。
