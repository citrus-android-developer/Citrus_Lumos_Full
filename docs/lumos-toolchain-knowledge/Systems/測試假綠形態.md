# 測試假綠形態（「測試存在，但沒在驗它宣稱要驗的」）

## 為什麼要有這張清單

這是本專案**撞最多次**的坑——累計 **16 次**。過去只有一句程序（**還原翻紅釘**：把 bug 還原回去，綁定測試必須翻紅）和散落在各個 Verification／Issues 節點裡的個案，**沒有一個地方把形態收攏**。

沒有清單的後果是：每次撞到都當成新的、當場想一個對策，下次換個外表又中一次。

## 九種形態（原稱八種；⑨ 於 2026-08-14 兌現「一定有第九型」的預言）

### ① 恆真斷言（期望值與被測邏輯同源）

斷言用**跟程式碼同樣的方式**重算期望值，所以它天生就會過、**永遠不可能跟程式碼唱反調**。

- 實例：等價驗證閘比較 `'' == ''`（空 vault 下兩邊都回空字串）；計劃裡寫 `assert ... or True`。
- 怎麼接住：**期望值必須來自獨立的真相來源**——已知良好的字面值、手算過的例子、規格條文。
- 出處：借自 mattpocock/skills 的 `tdd` skill（它叫 tautological）。★這是本清單唯一一條有外部現成定義的★。

### ② 斷言太鬆

判準寬到把「壞掉」也收進「過」。

- 實例：doctor 閘收 `rc in (0, 1)`——Python 未捕捉例外的 exit code 正好是 1，於是 NameError 也算過。
- 怎麼接住：對每個放行區間問「這個區間裡有沒有一種情況其實是壞的」。

### ③ 驗寫法不驗行為

斷言的是**原始碼長相**，不是**執行語意**。

- 實例：驗「`Write-Error` 後面緊接著 `return <int>`」——原始碼確實長這樣，但 `$ErrorActionPreference = "Stop"` 讓 `Write-Error` 變成終止型例外，那個 `return` 根本到不了。這條測試還做過 mutant 驗證、確認會翻紅，**仍然沒接住真缺陷**。
- 怎麼接住：問「把被測邏輯的**語意**（不只是字面）破壞掉，它會不會翻紅」。
- 實例（2026-08-04，[[Issues/loop-next吐不可宣告的tier]]）：`loop next` 吐的 `record_cmd`
  是**給人複製貼上的指令**。驗它「字串裡有沒有 `--tier legacy`」只證得了長相；
  ★真正該驗的是「這條指令跑得動嗎」★——把佔位符填掉、**原樣執行一次**、斷言 rc0。
  這一版的原缺陷正是「長得完全合理，但 argparse 當場 rc2」，字串斷言接不住。
  ★通則：測試的對象若是「一段要被別人執行的東西」（指令模板／產生的 script／
  複製貼上的片語），oracle 就該是「執行它」，不是「比對它」。★

### ④ 現場走不到被測分支 ★最隱蔽★

測試名稱、docstring、斷言看起來都對，但布置出來的現場讓**被測那條路一次都沒執行**。

- 實例：要驗「`rmdir` 失敗時的例外處理」，現場布置成「父目錄非空」——但那樣 `if ... and not any(parent.iterdir())` 直接判假，`rmdir()` 根本不會被呼叫，例外路徑零執行。**把修法還原成有缺陷的舊寫法，測試照樣全綠。**
- 怎麼接住：**要驗例外處理，現場就必須真的讓那個呼叫拋例外**，不能只是讓它不被執行。上例改成 `chmod ~/.local/share 0o500`（`unlink` 需要 `lumos-slim/` 的寫權限仍有、`rmdir` 需要 `share/` 的寫權限已無）後才真的翻紅。
- ★這一型是「還原翻紅釘」的盲區★，見下方硬規則。
- ★同日第二例，而且是**這個節點自己的綁定測試**★（2026-08-01 代碼審 r1 抓到）：`t_deinit_vendored_unlink_failure_does_not_abort` 把兩支 vendored 檔都放在同一個被 `chmod` 唯讀的 `scripts/` 底下，於是**兩支都刪不掉**——docstring 宣稱要驗的「其餘檔仍被移除（流程有走完）」**沒有任何斷言**，照那個佈置也不成立；另有一個建了卻沒用過的 `locked_dir` 死程式碼。把修法還原成裸 `unlink`，舊版**抓得到「炸例外」但抓不到「迴圈中斷、後面的檔沒被刪」**——而後者才是那條 `try/except` 真正要擋的回歸。修法：兩支檔分屬不同目錄、只鎖其中一個，且**會失敗的那支排在白名單第一個**；翻紅釘從 1 條翻紅變 4 條。
- ★這一例同時是第⑥型★（宣稱要驗的第②點根本沒去驗），說明**兩型會疊在同一條測試上**——分類是為了診斷，不是互斥的桶。
- ★第 12 次（2026-08-02，檢索多詞回退 M1）——又是這一型，而且又是**新測試自己犯的**★：`t_search_multiword_fallback_is_opt_in_and_only_on_zero` 要驗「片語真的存在時不得回退成 OR」，現場卻用「丙丁」當片語——**單一 token、中間沒有空白**。於是被測邏輯自己的前置守衛 `len(_fb_terms) > 1` 直接判假，**OR 路徑一次都沒被執行**；把 fallback-only 守衛拿掉（改成永遠 OR）的翻紅釘**照樣全綠**。修法：現場改成真的是多詞的「丙 丁」，**並另建一個只含單詞「丙」的節點當可被誤撈的靶**——★沒有那個靶，這條斷言就算走到了被測分支也沒有鑑別力（疊第⑤型）★。
  - ★這次新學到的通則★：**要驗「某條件成立時不得走某分支」，先確認現場真的滿足那條分支的全部前置條件。** 擋住你的往往不是你在測的那個守衛，而是**被測邏輯自己更前面的守衛**（這裡是「詞數 > 1」）——它不在你的注意力範圍內，卻決定了現場成不成立。
- ★第 13 次（2026-08-03，未閉合圍欄守衛）——**第④型的新面貌：現場不成立的原因是「指令用法就錯了」**★：要驗「`guard trace` 不得把未閉合圍欄裡的測試名當成合約佐證」，卻呼叫 `guard trace <測試名>`——**該指令吃的是節點不是測試名**，實際回 `ERROR: 找不到節點`，Verification 掃描那條路**一次都沒跑到**；而 `ERROR` 那行剛好也不含斷言要找的字串，於是斷言★碰巧★成立，把修法還原成 `FENCE_RE` 照樣全綠。
  - ★通則★：**前置斷言不能只證「fixture 檔案裡有那個字」，要證「被測那條路真的產出了它該產出的輸出」。** 這一例改成斷言輸出裡看得到 `[test:…] →` 那段證據鏈，翻紅釘才從 1 條變 3 條。
  - ★方法上的收穫（值得變成習慣）★：**先跑突變版確認它真的會誤報，再寫斷言。** 本例是先看到突變版印出 `→ 2026-08-03_demo`（誤報佐證）、還原版印出「無 Verification 提到此守衛」，確認現場有鑑別力**之後**才落斷言——順序反過來就會又寫出一條假綠。
- ★第 14 次（2026-08-03，同日第二次，**又是為了修上一輪 finding 而寫的測試**）★：要驗「`--code` 時範圍字串必須說『含程式碼區塊』」，fixture 卻讓完整片語在 code fence 裡**找得到**→ 加 `--code` 後**根本不觸發回退**，那個分支一次都沒執行；而斷言只寫「成功搜尋的 stderr 不含『可見文字』」——**沒有回退訊息時它必然成立**。翻紅釘從 2 條變 0 條，是 r4 跨家族審查員實跑才打臉。
  - ★修法★：現場改成「**即使含程式碼區塊，片語仍不連續**」，讓回退在兩種模式下都觸發，只有範圍措辭與**逐詞覆蓋數**會變（`午未:0 → 午未:1`）——後者是額外的鑑別力來源，而且它**同時當前置斷言**，證明 `--code` 真的生效。
- ★第 15 次（2026-08-03，Windows 真機回報的 rmtree 唯讀缺陷）——**跨平台語意差異造成的現場不成立**★：要驗「唯讀檔不得擋住 `rmtree`」，現場只 `chmod 444` 那個**檔案**——但 ★POSIX 與 Windows 的擋法根本不同★：Windows 靠**檔案的唯讀屬性**擋刪除，POSIX **只看父目錄的寫入權**、檔案自己 444 照刪不誤。於是 macOS 上兩種寫法都成功，把 `onerror` 拿掉的翻紅釘**照樣全綠**。修法：改成讓**父目錄**不可寫（POSIX 上真的會擋），並在註解裡寫明「這是可及的類比，不是與 Windows 相同的機制」。
  - ★通則（第④型的第三個面貌）★：**在 A 平台重現 B 平台的缺陷時，先確認「擋住它的機制」在 A 上也存在。**同一個 `chmod 444` 在兩個作業系統上是兩件不同的事——**語意差異會讓現場靜默失效**。
- ★第 16 次（2026-08-03，用真 PowerShell 驗 BOM）——**同一條測試裡疊了兩層現場不成立**★：
  - **第一層：用錯 API。** 想模擬 `irm | iex`，卻用 `[System.IO.File]::ReadAllText`——**它會自動剝掉 BOM**，根本沒模擬到。而且 `Parser::ParseInput`／`ScriptBlock::Create` **都容忍**開頭的 U+FEFF，**只有實際執行（`Invoke-Expression`）才失敗**——回報者的錯誤本來就是執行期 command-not-found，不是 parse error。
  - **第二層：`.NET` 的預設比對語意。** 改用保留 BOM 的讀法後，寫 `$first.StartsWith("#")` ——**`String.StartsWith(string)` 預設是文化相關比對，會忽略 U+FEFF 這類零寬字元**，第一個字元明明是 BOM 也回 `True`。翻紅釘連跑兩次都全綠，改成 `$first[0] -ne [char]0x23` 才紅。
  - ★通則★：**「我用的這個 API，它的預設行為真的是我以為的那樣嗎？」** 本例連踩兩個預設：`ReadAllText` 預設剝 BOM、`StartsWith` 預設忽略零寬字元。★兩個都不是 bug，都是文件寫好的預設——錯在我沒查★。
  - ★這四次（12/13/14/15）的共同結構值得單獨記★：**都是「為了修 finding 而新寫的測試」自己中第④型**。趕著補洞時最容易只想「斷言寫什麼」而不想「現場走不走得到」。★收尾的翻紅釘不是形式——它是唯一會告訴你現場沒成立的東西，而且要看**翻紅幾條**，不能只看有沒有紅。★

### ⑤ fixture 產不出有鑑別力的值

現場太貧乏，好的實作與壞的實作在它身上給出同一個答案。

- 實例：等價驗證跑在**空 vault** 上，把 `cmd_search` 整個掏空，10/10 仍然全過。
- 怎麼接住：問「這個 fixture 底下，正確實作與被我弄壞的實作，輸出真的會不同嗎」。與①常同時出現，但成因不同：①是斷言寫法，⑤是資料太弱。

### ⑥ 根本沒去驗

不是斷言寫錯，是**壓根沒有任何一條測試碰過那個行為**。

- 實例：卸載器留下 `~/.local/share/lumos-slim/manifest.json`，彙總卻印「✓ 全部完成」——**2011 條測試沒有任何一條斷言過它該消失**。是對打包後產物做端到端真跑才發現的。
- 怎麼接住：靠**測試邊界事先議定**（見下方「未採納」）與**對交付產物的端到端真跑**。加測試數量接不住這一型。

### ⑦ 守衛的白名單過寬

守衛本身有效，但它的例外清單寬到把新出現的違規一起放行。

- 實例：README 懸空引用守衛用 `(token, form)` 當白名單——同一個 token／form 出現在**檔案任何一行**都被靜默放行。
- 怎麼接住：白名單綁**唯一定位**（四元組 `檔名+行號+token+form`，或綁該段獨有的特徵字串），不要綁類別。

### ⑧ 依賴環境巧合

同一份碼、同一棵樹，綠或紅取決於執行環境的偶然性質。

- 實例：交付薄殼呼叫外部 `dirname`，而測試刻意把 PATH 縮到最小；互動 shell 的 `git` 在 `/usr/bin`（那裡有 `dirname`）→ 綠，hook 底下的 `git` 在 CommandLineTools（沒有）→ 紅。
- 怎麼接住：問「這條測試的綠紅，會不會取決於這台機器裝了什麼、裝在哪」。見 [[Issues/prepush測試閘假紅-git環境洩漏]]。

### ⑨ 合約文字寬於測試覆蓋（宣稱的行為從未被執行過）

合約／文件宣稱一個行為，也綁了測試、甚至蓋了審計標記——但綁的測試只走過宣稱的
**子集**，宣稱的其餘部分**從來沒有被任何測試、任何生產流量真的執行過**。
死文字錯了不會有人知道；它甚至可能**結構上不可能發生**。

- 實例（2026-08-14 Landmark）：合約寫「一單多會員票券→**每核銷會員一列**」並綁測試＋
  審計標記；但綁定測試只蓋**單券主**。實查該表主鍵=(StoreID,OrderNO,PayNo)——
  ★宣稱的「多列」結構上不可能，第二列會撞 PK 炸掉整筆交易★。
  七輪對抗審 14 席都沒從 code 讀出來（大家驗「合約文字內部一致」），
  最後靠迴歸測試意外撞上＋業主一句「還是兩列嗎？」拆雷。
- 怎麼接住：合約每一句**行為宣稱**都要問「哪支測試真的走過這句？」走不到的那半句，
  要嘛補測試、要嘛把宣稱收窄到已驗範圍。★機制宣稱另加一問：schema（主鍵/唯一索引/
  CHECK）允許這個行為發生嗎？★——schema 對合約的交叉驗證是獨立於 code review 的一面鏡子。
- 本型正是本清單 KEY 行「★假設一定有第九型★」的兌現。外部文件仍稱「八型清單」者係舊稱。

## ★硬規則：翻紅釘必須配「現場成立」前置斷言★

「還原翻紅釘」是本專案接住假綠的主力做法，但它**對第④型完全瞎**：現場走不到被測分支時，把修法還原回去，測試照樣全綠。

所以修 bug 收尾時：

1. 把修法還原 → 綁定測試**必須翻紅**（原有規則）
2. **★同時放一條前置斷言，證明現場真的成立★**——被測那條路真的被執行到了

寫法（本專案已自發長出的慣例，此處正式定為規則）：

```python
check("★前置★ 現場成立:rmdir 這一步真的拋了例外(輸出有順帶清理沒成功的字樣)",
      "順帶清理空目錄" in out, out)
```

前置斷言失敗 ＝ **這條測試根本沒在測它宣稱要測的東西**，比主斷言失敗更該優先修。

### ★第二個盲區：翻紅釘的紅必須來自目標檢查（斷言重疊，2026-08-04）★

翻紅釘「有翻紅」不等於「目標檢查在守」——**現場若同時違反多條檢查，把目標檢查拔掉後，鄰近檢查會用同一個 rc「代打」**：釘照樣紅，但那是假紅，目標檢查其實沒被任何測試守住。

- 實例（design-loop 落地 T1，record 處置集合核對）：「缺 c 未處置必 rc2」的現場**同時**漏給 accept 理由——把聯集檢查註掉，理由檢查代打 rc2，釘紅得理直氣壯。修法＝把理由給齊，讓聯集檢查成為**唯一能翻紅的路**，才真的紅在該紅的地方。
- 怎麼接住：**佈置現場時把目標檢查以外的檢查全部餵到滿足**；rc-型斷言儘量同時斷錯誤訊息（哪一條檢查在叫），不要只斷 rc。
- 與「現場成立」前置合起來是一對：前置斷言證「被測那條路走得到」（守現場），本條證「翻紅的路只有目標這一條」（守鑑別力）。

## 誠實天花板

- **★假設一定有第九型★。** 這張清單是「我枚舉了 N 種形態」，而本專案已被這句話打臉多次（掃描器五形態掃不到路徑型；CLI 自揭未交付指令列了三支、複審查出第四支）。
- **★不得把「對照過清單」當成「測試夠格」的證明★。** 清單是提示器不是偵測器；漏網靠 canary、對抗審、與對交付產物的端到端真跑兜。
- **mutant／翻紅釘證明的是「這條測試接得住我預期的失效模式」，不是「接得住真正的失效模式」**（既有結論，仍然成立）。
