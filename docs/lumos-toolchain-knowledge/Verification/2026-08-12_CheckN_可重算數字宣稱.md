# 驗證：Check N（可重算數字宣稱）

## 用真實錯誤當回歸案例

不是造假資料測，是**把兩個月前真實發生過的錯誤重演一次**：

`點數商城` 的 BrandID 放寬處數，架構圖長期寫「共 5 處」「5 處全部放寬」，2026-08-12 實證是 **7 處**。
把該行植入標記後：

```
<!--lumos:count=7 re=ISNULL\(VT\.BrandId, ''\) = '' in=**/PointsMall*.cs-->
```

- 宣稱 7 → `✓ 1 個可重算數字宣稱全部對得上`
- 故意改成 5 → `⚠ Systems/點數商城.md → 宣稱 5 / 實測 **7**`

★**印出來的字，就是當初那個錯誤的原文**★。

## 測試（6 條）

| 測試 | 守什麼 |
|---|---|
| `t_checkn_matches_when_count_correct` | 對得上不吵 |
| `t_checkn_reports_drift` | ★核心★ 漂移要**同時報宣稱值與實測值**，不能只說「有問題」 |
| `t_checkn_soft_does_not_fail_ci` | 軟提醒不影響 rc |
| `t_checkn_bad_regex_does_not_crash` | ★壞正則吞成提示不炸 doctor★（節點內容是使用者輸入） |
| `t_checkn_glob_scopes_the_count` | `in=` 真的有縮範圍（否則數字沒意義） |
| `t_checkn_silent_without_markers` | 無標記時給引導不報錯 |

全套 **2555 passed / 0 failed**。

## 為什麼這條特別值得做

2026-06-10 的首輪交叉審計**已經把這條寫成教訓**——「計數/清單型主張最會漂」。
**但沒有配機制**，於是 2026-08-12 那輪在五個批次裡**每一批都復發**。

> ★「寫進教訓」和「有機制擋」之間的落差，就是這兩個月裡五次重複犯錯的全部原因。★
