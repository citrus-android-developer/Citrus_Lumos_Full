# 2026-08-01_slim-終審三缺陷修復

## 背景

分支終審(對抗代碼審)抓到三條缺陷,全部圍繞在 Task 13~15 已交付的 Windows/PowerShell 支援與卸載邏輯上:

1. **①BLOCKER**:三支 `.ps1`(`install.ps1`/`uninstall.ps1`/`get.ps1`)頂部都設 `$ErrorActionPreference = "Stop"`。PowerShell 語意:`Stop` 會把 `Write-Error` 這種非終止型錯誤升級成終止型例外(等同 `throw`)。後果:`Write-Error` 那行直接拋例外 → 它後面的 `return <int>`(Task 15 的反向斷言驗的正是這一行的長相)是死碼,執行不到 → 例外炸穿 `Invoke-Install`/`Invoke-Uninstall`/`Invoke-Get` → 連 `$rc = Invoke-* ...` 的賦值都完成不了 → 檔尾 `$global:LASTEXITCODE = $rc` 永遠不執行 → 呼叫端讀到殘留舊值(很可能是 0)、把失敗誤判成成功。這正好打掉 Task 14/15 整段修法的目的,而且發生在它最該保護的錯誤路徑上。**這是本專案第十次撞到「測試存在但沒在驗它宣稱要驗的」**——Task 15 的 `t_slim_ps1_error_branches_still_halt_via_return` 驗的是原始碼長相(Write-Error 後面那行寫的是不是 `return <int>`),不是執行語意(那一行執行到時 Write-Error 本身會不會先拋例外讓 return 永遠執行不到)。
2. **②MAJOR**:`slim/uninstall.py` 的 `if dst_script.exists() or dst_script.is_symlink():` 把整個 `lumos.cmd`(`dst_shim`)移除邏輯都巢狀在底下。`lumos` 不存在但 `lumos.cmd` 還在(使用者手滑刪了 `lumos`,忘了刪 `.cmd`)時,外層 `if` 判假,整段(含 `--force` 分支)都跳過,孤兒 `lumos.cmd` 永遠清不掉——牴觸 `uninstall.py` 自己 docstring 講的「兩者總是成對安裝/移除」,也是 [[Systems/slim-install-安裝器]] Task 14②已修過的「碰撞偵測要同時看兩個檔案」的鏡像缺口。
3. **③MINOR**:`get.ps1:38`(修復前行號)的 `$ErrorActionPreference = "Stop"` 是裸賦值,寫在函式外的頂層。README 教的一行安裝 `irm ... | iex` 中,`iex` 在**呼叫端當下的 scope** 執行(不像 `& "path.ps1"` 會建新 script scope),這行會改到使用者互動 shell 的設定,且裝完不還原——同一視窗裡任何原本靠非終止型錯誤運作的後續指令都會被意外中止,使用者不會知道原因是「剛剛裝了個東西」。`install.ps1`/`uninstall.ps1` 因為經 `&` 呼叫有自己的 scope,不受影響。

## 修法

**①** 每一處 `Write-Error` 呼叫都明確加 `-ErrorAction Continue`(6 處:install.ps1 1、uninstall.ps1 1、get.ps1 4)——這是 PowerShell 官方支援的逐次呼叫覆寫機制,對單一 cmdlet 呼叫的 `-ErrorAction` 會蓋過 `$ErrorActionPreference` 這個全域偏好設定。選這個而不是 try/catch 或改用 `[Console]::Error`,理由:①官方支援的逐次呼叫覆寫,語意上最直接對應意圖②維持既有「Write-Error 後緊接 return」結構,不必重新設計成 try/catch 包住整段函式③訊息仍然真的走 Write-Error(進 stderr、保留 PowerShell 錯誤記錄語意),不是換一套機制。`$ErrorActionPreference = "Stop"` 本身**保留**(其餘沒有明確覆寫的 cmdlet 仍該終止就終止,這是刻意保留的行為,只放行 Write-Error 這條刻意設計成非終止的分支)。

**②** `uninstall.py` 的 `~/.local/bin/lumos.cmd` 處理邏輯移出 `~/.local/bin/lumos` 的 if 區塊,改成獨立的「①b」區塊(僅 `IS_WIN`),與①各自獨立判斷、各自執行、互不阻擋——呼應本專案 Task 10 已定的「卸載各步互不阻擋」原則。安全判斷依據:shim 沒有 manifest 雜湊可比對(shim 內容是固定樣板、跟安裝位置無關,拿它比對沒有鑑別力),改用「內容是否符合 `install.py` `_install_cli()` 產生的固定樣板」(`SHIM_TEXT_RE = r'\A@echo off\r\n(?:python3|python) "%~dp0lumos" %\*\r\n\Z'`)當基準:符合視為本包裝的 shim,可安全移除(不需要 `--force`);不符合當成使用者自己的東西,拒絕移除(要砍就 `--force`)。★踩到的一個實作坑★:第一版用 `dst_shim.read_text(encoding="utf-8")` 讀取內容比對,但 `Path.read_text()` 預設 universal-newline 轉譯,會把 shim 內容裡的 `\r\n` 正規化成 `\n`,即使檔案位元組完全沒被動過,也讓比對 `\r\n` 的 `SHIM_TEXT_RE` 永遠比不到——新測試第一輪就抓到這個(`t_slim_uninstall_windows_orphan_cmd_shim_removed` 翻紅),改成 `read_bytes().decode("utf-8")` 修正。這正是 `t_slim_install_windows_collision_detects_orphan_cmd_shim` docstring 已經點過一次的同一個坑,在讀取端的鏡像版本。

**③** `get.ps1` 的 `$ErrorActionPreference = "Stop"` 從頂層移進 `Invoke-Get` 函式內部第一行——PowerShell 函式預設有自己的子 scope,函式內對變數賦值(沒加 `$global:`/`$script:` 前綴)只落在函式自己的 local scope,不會外溢回呼叫端。`Invoke-Get` 函式本體已涵蓋本檔案所有用到非終止型錯誤語意的邏輯,搬進去不影響行為。`install.ps1`/`uninstall.ps1` 原本就不受這個污染問題影響(經 `&` 呼叫、本來就有自己的 script scope),但一併搬進函式維持三支檔案寫法一致(純一致性處理,非修真缺陷)。★頂層的 `$Pkg = Split-Path -Parent $MyInvocation.MyCommand.Path` 刻意留在函式外★:`$MyInvocation` 在函式內部會變成指向函式自己的呼叫資訊,搬進函式會改變 `.MyCommand.Path` 的語意。

## 測試

**★誠實限制★(①③)**:這台機器沒有 PowerShell,只能做靜態結構驗證,不能驗真實執行語意。

1. 新增 `t_slim_ps1_write_error_noterminating_under_stop_preference`——驗得到:三支檔案的 `$ErrorActionPreference = "Stop"` 賦值仍在;每一處 `Write-Error` 呼叫那一行本身帶有 `-ErrorAction Continue`/`SilentlyContinue`/`Ignore`(不是猜隔壁行、不是整份檔案子字串比對);`Write-Error` 出現次數符合預期(6 處);結構順序上 Stop 賦值出現在所有 Write-Error 之前(近似執行順序,非控制流分析)。**驗不到**(核心誠實聲明):`-ErrorAction Continue` 在真實 PowerShell 執行時是否確實蓋過 `$ErrorActionPreference`(這是 PowerShell 官方文件記載的行為,但沒有真機可以實際執行一行 `$ErrorActionPreference = "Stop"; Write-Error "x" -ErrorAction Continue; Write-Host "still alive"` 去驗證「still alive」真的印得出來);函式 scope 內對 `$ErrorActionPreference` 的區域賦值在函式呼叫當下是否真的先於函式內任何 cmdlet 生效,是 PowerShell scope 解析規則,同樣沒有真機可以驗;`$LASTEXITCODE`/`$global:LASTEXITCODE` 在各種呼叫路徑下是否真的對呼叫端可見,一樣需要真機驗證。**不把 mutant 驗證當作「測試夠格」的證據**——mutant 只證明「抓得到我想到的這一種失敗模式」,不證明「抓得到 PowerShell 真實執行時所有可能讓 Write-Error 變終止型的失敗模式」。
2. 新增 `t_slim_uninstall_windows_orphan_cmd_shim_removed`——用 `LUMOS_SLIM_SIMULATE_WINDOWS=1` 真實裝一次(產生真正的 `lumos`+`lumos.cmd` 配對,shim 內容是 install.py 實際偵測出的直譯器,不是自製假字串),手動只刪 `lumos`(模擬使用者手滑),留下孤兒 `lumos.cmd`;跑一次不帶 `--force` 的模擬 Windows 卸載,斷言 rc0 且孤兒 `lumos.cmd` 確實被清掉(不需要 `--force`,因為內容比對得上樣板)。
3. 新增 `t_slim_uninstall_windows_orphan_cmd_shim_foreign_content_needs_force`——對稱驗證:孤兒 `lumos.cmd` 若內容不符合樣板(可能是使用者自己的東西),不帶 `--force` 應該拒絕移除(rc=1,安全性跳過)、帶 `--force` 才能覆蓋,證明②的修法不是矯枉過正變成「lumos 不存在時無腦刪掉任何 lumos.cmd」。
4. 紅→綠實測(②,非稻草人):`git stash push -- slim/uninstall.py` 還原成本次修復前的舊版(新測試已寫好、code 未改),重跑 `python3 scripts/test_lumos.py -k orphan_cmd_shim`——15 checks 中 3 個翻紅:「★孤兒 lumos.cmd 確實被清掉(不是永遠殘留)★」(舊版對孤兒現場整段不處理,連印都不印)、「★內容不符本包樣板 → rc1(安全性跳過,非硬錯誤)★」(舊版永遠 rc0,不會主動拒絕)、「--force 後檔案確實被移除」(舊版 `--force` 分支同樣巢狀在 dst_script 的 if 裡,救不了孤兒殘留)。`git stash pop` 還原後重跑,15 checks 全綠。
