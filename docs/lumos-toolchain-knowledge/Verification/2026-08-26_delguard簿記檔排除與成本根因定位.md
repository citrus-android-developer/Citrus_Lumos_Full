# 2026-08-26_delguard簿記檔排除與成本根因定位

[[Verification/2026-08-26_delguard超時分類與降級訊息修復]] 的續篇。該篇修了「閘沒跑卻看不出來」,本篇處理「閘為什麼常常跑不完」——**修掉一半,另一半定位完成但未動手**。

## 已修:簿記檔不抽 token

`*.jsonl` 帳本與 `anchor-baseline.json` 的刪除行不再抽 token。這些檔的內容是**紀錄**不是宣告,刪掉一行從來不代表「某個符號沒了」。

★不只是效能問題★:修前,治理帳一變動就會報出「code 側刪除傳播」命中——fixture 實測 `tokens: 7`、**1 筆假命中**,但根本沒有 code 被刪。這是純假陽性,而假陽性會訓練人忽略這道閘。

順帶消掉的成本來源:治理帳 JSONL 的欄位名(`commit`/`gate`/`kind`/`nodes`/`hard`)與 sha、時間戳碎片會被當成被刪符號。實測同一個 commit 的 token 數從 115 降到 46。

## 已定位、未修:成本根因

先後推翻三個假設,最後量到真因。

| 假設 | 量測 | 結論 |
|---|---|---|
| 完整掃描量太大 | git diff 0.02s / parse 0.00s / vault_scan 0.21s / **_delguard_confidence 159.97s** | 成本 99.9% 集中在一段 |
| 717KB 壓縮 JS 單行(`scripts/vendor/`)是元凶 | 排除後 81.75s,原 81.93s | ✗ 推翻 |
| 逐 token 早退會快很多 | 死 token 最壞情況合併 0.01s、逐個 0.20s | ✗ 早退不是關鍵 |
| `-w` 旗標造成退化 | 不帶 `-w` 是 97.23s,比帶的 83.71s **更慢** | ✗ 推翻 |

真因:**git grep 的 pattern 數量**。同一組檔案、同樣旗標——

- 1 個常見 token → **0.03s**
- 10 個常見 token → **83.71s**

單 pattern 走快路徑,多 pattern 退化。這也解釋了為什麼死 token 很快(輸出為零)、為什麼排除 vendor 沒用(與掃描量無關)。

★候選解★:改成逐 token 各跑一次 grep(0.03s × 40 ≈ 1.2s,對比現況 160s)。**未實作**——這會動到本系統 summary 宣告的「單次 git grep」設計,該設計原意是避免 N 次 subprocess 生成,但量測顯示 N 次生成遠比多 pattern 退化便宜。

## 驗證

1. **先紅後綠**:`_mk_delguard_bookkeeping_repo` fixture 打在修前版本得 `tokens=7` / 1 筆命中,修後 `tokens=0` / `hits=[]` / `degraded=false`。
2. **全量測試**:2877 passed / 0 failed(基線 2874 + 3)。
3. **量測**:上表四列各為實跑輸出,非估算。`-w`/`-n` 兩組的絕對值(97.23s / 108.59s)與 83.71s 同量級,差異含併發測試造成的雜訊,★不應解讀其排序★——可判定的只有「都與旗標無關」。
