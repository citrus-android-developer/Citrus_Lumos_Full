# 2026-08-03 Windows 回歸測試三缺陷

## 一句話

**v1.4 修好了磁碟執行，卻弄壞了 README 唯一教的那條指令——BOM 從來不是解法，是把問題搬家。**

## 三條

| | 缺陷 | 是不是 v1.4 造成的 |
|---|---|---|
| ① | BOM 讓 `irm \| iex` 的第 1 行被當成指令執行 | **是**（v1.4 的修法本身） |
| ② | `install.py` 的 skill 備份仍留在 `~/.claude/skills/` | 前一輪只修了卸載端 |
| ③ | `param($Pkg, $Args)` 讓所有旗標靜默失效 | 否，前一版包函式時就在 |

## ★① BOM 的兩難★

| 執行路徑 | 無 BOM | 有 BOM |
|---|:--:|:--:|
| 磁碟執行 `& install.ps1` | ✗ ANSI codepage 誤解碼 | ✅ |
| `irm … \| iex`（README 唯一教的） | ✅ | ✗ `U+FEFF` 進第 1 行 |

**正解是消滅問題不是搬家：ASCII-only 之後兩條路徑都不需要 BOM。**
中文說明搬 `slim/WINDOWS-NOTES.md`。

★**而這條紀律，組織內部早就寫下來了**★——`LandmarkMember` 的 `CLAUDE.md`
〈Deploy 腳本踩雷規則〉第 1 條「ASCII-only 規則」，理由一字不差，
**是踩了 v1.0.15／16／17 三輪 prod deploy 失敗才立的**。

★**我設計這幾支檔案時，從沒去查過。**★ CLAUDE.md 的第一條就是「架構圖先行」。

## ★② 安裝端漏修，而且比卸載端更糟★

卸載器只認 `lumos-project-notes` 這個名字，**不會清安裝端留下的 `.bak.<ts>`**
——所以那份備份會**永遠留在 skills 目錄裡持續被當成 skill 載入**。

兩邊現在用同一個落點。★不同落點就等於又製造一次「同一件事兩份實作」★，
那是本專案今天已經收編過三次的形狀。

## ★③ 「沒人用過的路徑不會有人回報」★

`$Args` 是 PowerShell 自動變數，同名 `param` 會被它蓋掉，`@Args` 展開成空。
**前一份真機回報沒抓到，是因為當時沒傳過任何參數。**

## ★★推翻「這台機器沒有 PowerShell」這個免驗證通行證★★

我在多個節點寫過「開發機是 macOS，一行 `.ps1` 都跑不了」，並據此把好幾條測試
標成「只驗原始碼長相（假綠第③型），刻意如此」。

**那句話對其中兩個機制是錯的。** `pwsh` 7 可以 `brew install`，而：

| 機制 | 是不是 Windows-only | 本機實測結果 |
|---|---|---|
| `$Args` 自動變數遮蔽 | ❌ 語言層，跨平台一致 | `param($Args)` → count=**0**；`$ScriptArgs` → count=**2** |
| BOM 讓 `iex` 炸第 1 行 | ❌ 語言層 | `The term 'Windows/PowerShell' is not recognized`（**與回報一字不差**） |
| 磁碟執行用系統 ANSI codepage 讀檔 | ✅ 真的是 Windows-only | 仍未驗 |

★**通則**★：遇到「跨平台語言層行為」，**不要直接套用「沒有那個執行環境」這個免驗證通行證
——先問它到底是不是該平台獨有的行為。**

測試因此升級成**真的跑 pwsh**（沒有 pwsh 時明確 skip，不假裝驗過）。

## 第 16 次測試假綠（同一條測試疊了兩層）

**第一層：用錯 API。** 想模擬 `irm | iex`，用了 `[System.IO.File]::ReadAllText`
——**它會自動剝掉 BOM**。而且 `Parser::ParseInput`／`ScriptBlock::Create` **都容忍**
開頭的 `U+FEFF`，**只有實際執行才失敗**。

**第二層：`.NET` 的預設比對語意。** 改用保留 BOM 的讀法後寫 `$first.StartsWith("#")`
——**`String.StartsWith(string)` 預設是文化相關比對，會忽略 `U+FEFF` 這類零寬字元**，
第一個字元明明是 BOM 也回 `True`。

**翻紅釘連跑兩次全綠，第三次才紅。**

★通則★：**「我用的這個 API，它的預設行為真的是我以為的那樣嗎？」**
本例連踩兩個——`ReadAllText` 預設剝 BOM、`StartsWith` 預設忽略零寬字元。
**兩個都不是 bug，都是文件寫好的預設；錯在我沒查。**

## 誠實邊界

- 「磁碟執行被 ANSI codepage 誤解碼」那一半**仍未在真機驗過**——但 ASCII-only 讓它
  **在原理上不可能發生**（沒有非 ASCII 位元組就沒有 DBCS 前導位元組），
  這比 v1.4 的「加 BOM」是更強的保證。
- 三支 `.ps1` 的**整體執行流程**（真的裝、真的卸）仍未在真機 Windows 上跑過。
