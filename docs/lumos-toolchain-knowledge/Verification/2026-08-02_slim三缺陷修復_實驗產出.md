# 2026-08-02_slim 三缺陷修復（對照實驗的產出）

## 一句話

**審查規模的對照實驗本來是要測「大 payload 會不會漏看」，結果順手撿到三個真缺陷——而其中一個，已經裝在別人電腦上了。**

## 修了什麼

### ① 卸載器七處裸的檔案寫入 —— 違反已宣告的硬合約（major）

`slim/uninstall.py` 的 `_restore_claude_md()`（步驟④）與步驟①/①b 的 `unlink()`／`write_text()` 全是裸呼叫，`main()` 呼叫它們時也沒有 try。

CLAUDE.md 唯讀、磁碟滿、或 Windows 上檔案被別的程式鎖住時 → `PermissionError` **直接炸穿 `main()`**，排在後面的步驟⑤（清 manifest）**一次都不會執行**，使用者只拿到一段 traceback。

這**直接違反** [[Systems/slim-uninstall-一行卸載]] 2026-07-31 就宣告的硬合約「各步互不阻擋」。

> **合約條文自己也有洞**：原條文只寫「任一步驟基於**安全考量跳過**絕不能連帶阻止其餘步驟」——只枚舉了「主動跳過」，沒枚舉「拋例外」。而 code 裡活著的正是沒被枚舉的那一種。**條文枚舉不完整，守衛就有洞**，同 [[Systems/測試假綠形態]] 的「假設一定有第九型」。條文已補。

**修法**：每個檔案系統寫入各自 `try/except OSError` → 印警告 + `bump(2)` 交給彙總，與本檔既有錯誤路徑（多 sentinel、base64 解碼失敗）一致。

### ② 安裝器的例外會噴 traceback（minor）

`slim/install.py` 沒有任何檔案系統例外處理，`PermissionError` 的堆疊直接丟給使用者。

★**這裡刻意沒有照 ① 的做法修**★。install 的 `main()` 是**遇錯早退**（`rc != 0` 就 return）——每一步依賴前一步，裝到一半就該停，而不是把 skill 裝進一個沒有 CLI 的環境。把 uninstall 那套「包起來繼續跑」搬過來會**改掉它的順序語意，那不是修 bug 是製造 bug**。

**修法**：只在最外層加 `_main_guarded()` 接 `OSError` → 一句可行動訊息（常見原因 + 排除後重跑 `--force`）+ rc2。**控制流一行都沒動。**

半成品狀態（CLI 裝好了、skill 沒裝成）是**已知且刻意保留**的——精簡版不做交易式回滾（回滾自己也會失敗，而且刪使用者的東西風險比留著高）。測試因此**刻意不斷言**「已完成步驟被回滾」——斷言不存在的行為會變成假需求。

### ③ `get.ps1` 的 `git clone` 漏檢 `$LASTEXITCODE`（minor）

同一個函式裡 `git pull` 有檢查、`git clone` 沒有，純粹是漏寫的不對稱。

不能靠 `$ErrorActionPreference = "Stop"` 兜底：它只管 PowerShell cmdlet，**原生執行檔回非零 exit code 不會觸發終止**（PS 7.3 起的 `$PSNativeCommandUseErrorActionPreference` 才改這行為，而本包要支援 Windows PowerShell 5.1）。

後果不是靜默失敗，是**把查錯方向帶偏**：clone 失敗（沒網路／私有 repo 沒權限／磁碟滿）後照樣往下走，使用者看到的是下一段那句「交付包內容可能不完整」——網路／權限問題被講成「這個包壞掉了」。

## 怎麼驗的

五條測試各自跑過**還原翻紅釘**，且每條都配「**現場成立**」前置斷言（[[Systems/測試假綠形態]] 的硬規則——沒有前置斷言的翻紅釘對第④型「現場走不到被測分支」完全瞎）：

| 缺陷 | 現場（真的讓那個呼叫拋例外） | 還原修法後翻紅 |
|---|---|---|
| ① | `chmod CLAUDE.md 0o444`，區塊移除後新內容非空 → 走 `write_text()` → 對唯讀檔開 `'w'` 必定 `PermissionError` | **4 條**，輸出真的印出 `PermissionError` 炸穿 `main()` 的完整堆疊 |
| ② | `chmod ~/.local/bin 0o500` → `shutil.copyfile()` 寫不進去 | **4 條** |
| ③ | 拿掉 clone 後的 `$LASTEXITCODE` 檢查 | **1 條** |

**①② 的 rc 斷言刻意釘死 `== 2`，不收 `in (1, 2)`** ——未捕捉例外的 exit code 正好是 1，收寬就掉進第②型「斷言太鬆」。

## ④⑤ 修法自己漏掉的另一半 —— 單 reviewer 抓到（比上面三條更值得記）

上面三條修完之後派了一席 reviewer（`tier: standard`），**它交回兩條 major，都附可重現指令，都是真的**：

| | 缺陷 | 為什麼第一版修法蓋不到 |
|---|---|---|
| ④ | `slim/uninstall.py:118` `read_text()` 在 try 外面 | 我把缺陷描述成「裸的**檔案系統寫入**」，於是 AST 掃描器只掃 `unlink`/`write_text`/`rmdir`… **「讀」根本不在清單裡** |
| ⑤ | `slim/install.py` `_main_guarded()` 只接 `OSError` | `_merge_claude_md_text()` 讀的是**使用者既有的** CLAUDE.md，編碼不歸我們管 |

兩條的共同核心：★**`UnicodeDecodeError` 繼承 `ValueError`，不是 `OSError` 子類**★——所以連我剛加的 `except OSError` 都攔不到。

觸發完全不刁鑽：CLAUDE.md `chmod 000`，或內容不是合法 utf-8（**中文專案裡別的編輯器存成 Big5、貼進壞位元組都很真實**）。症狀跟修之前**一模一樣**：traceback 炸穿 `main()`、步驟⑤永遠不執行、rc=1。

> **本檔 ①b 段讀 shim 內容時，就是同時接 `OSError` 與 `UnicodeDecodeError` 兩種。** 那裡對了，這裡漏了——是不一致的疏漏，不是刻意的範圍決定。

**修法**：讀取側兩種例外分開接、各回一句對應的 rc2 訊息；install 側補獨立 except 分支，訊息明講「本安裝器只處理 utf-8，不會在看不懂內容的情況下改寫你的 CLAUDE.md」，並斷言該檔**位元組原封不動**。

★**這條的教訓不是「要多接一種例外」**★，是：

> **用來描述缺陷的那個詞，會決定你之後漏掉什麼。** 把它叫做「裸的檔案系統**寫入**」，後續的掃描器、修法、測試、連架構圖條文全部只涵蓋「寫」。**描述本身就是一道過濾器**，而且是靜默的。

這跟 ① 的「合約條文只枚舉了一種失效形態」是**同一個形狀**，一天之內撞兩次。

全套：**2082 → 2119 條全綠**（5 條新測試、38 條斷言，翻紅釘分別翻紅 4/4/1/**8**/**3** 條）。

## ⑥ 對交付包端到端真跑，又抓到一條訊息不對稱

把修好的檔放進交付包、在假 `HOME` 上真跑三個現場（唯讀／讀不到／非 utf-8）**全部正確**。但順帶看到一件事：`OSError` 那條錯誤訊息有講「★已完成的步驟不會被回滾★」，**`UnicodeDecodeError` 那條沒講**——而那時 ①CLI 與 ②skill 其實已經裝好了。不講的話，使用者會以為整件事失敗、跑去手動清理已經裝好的東西。

★**訊息不對稱本身就是缺陷**★，已補齊並綁上斷言（含一條「前置：①②這時真的已經裝好了」——否則那條斷言是在講一件沒發生的事）。

> **這是本專案第三次由「對打包後產物做端到端真跑」接住測試套件看不到的東西。** 前兩次分別是 manifest 殘留、以及這次。單元測試驗的是行為對不對，真跑才看得到**使用者實際讀到什麼**。

### 這次踩到的坑（記著）

`t_slim_get_ps1_every_git_call_checks_lastexitcode` 第一版的正則掃全行，把**錯誤訊息字串裡**的「找不到 git 指令」「不是本包的 git clone」也算成 git 呼叫，三條斷言當場紅一條。字串裡的 git 不是呼叫。改成只認行首（可帶變數指派）的呼叫。

★**值得記的是：那條「前置：真的找得到 git 呼叫行」的斷言當時是綠的**★——它只檢查數量 ≥2，抓不到「找到的是錯的行」。**前置斷言證明的是「有東西被找到」，不是「找對了」。**

## 誠實邊界

- **③ 是 [[Systems/測試假綠形態]] 第③型（驗寫法不驗行為），而且刻意如此**——開發機是 macOS，沒有 PowerShell，**一行 `.ps1` 都跑不了**。那條測試買到的只有「新增 git 呼叫時不會忘了配一道檢查」這個對稱性。★**不得因為它綠了就宣稱 `get.ps1` 在 Windows 上正確**★。已知限制：管線中段的 git（`... | git ...`）抓不到。
- **① 的修法只證「`OSError` 這條路走得通」**，不證所有失效模式都接得住（`KeyboardInterrupt`／`MemoryError` 不是 `OSError` 子類，照樣炸穿——這是刻意的，那些本來就該中止）。
- **已重新交付**：`github.com/citrus-android-developer/Citrus_Lumos` main = `9fbc5a6`，tag **`v1.2-handoff`**（2026-08-02 推送並確認遠端）。交付 diff **只動 `install.py`／`uninstall.py`／`get.ps1` 三支**，`scripts/`（產生物）與 `skills/` 一個位元組沒動——重生 `scripts/lumos` 的差異只有一個死常數加註解、無功能變動，★刻意不送★，讓交付 diff 恰好等於這次的修復本身、可審。交付前對打包後的包本身做過端到端真跑（正常／唯讀／讀不到／非 utf-8 四情境全對）。★交付包的註解另外去掉了內部術語★（「對照實驗抓到」「單 reviewer 抓到」對接手的人沒有上下文）。

## 這件事本身的教訓

★**這三條不是 reviewer 抓到的**★。四席審過同一份 code：

| payload | 結果 |
|---|---|
| **610 行**（1 席） | **找到 ①**，標 major，還實測 `Path.unlink()` 行為佐證 |
| **2770 行**（3 席） | **三席全部正面宣稱它沒問題**——「沒有任何一步用 return/exit 中止其他步驟」「`OSError` caught around **every** filesystem mutation」「邏輯正確，除 finding 1 外無其他問題」 |

三席用的都是最強的正面措辭，不是含糊帶過。缺陷是**編碼 [[Projects/規模影響判斷力假說]] 的③（偽陰性斷言）時逐條查地面真相**才浮出來的。

**這對 lumos 的 gate 是直接的**：收斂閘把「乾淨輪」當品質證據，但如果大 payload 產出的是**有把握而錯的「沒問題」**，那種乾淨輪的證據力是虛的。

★**但這還不能動 gate**★——見 [[Projects/規模影響判斷力假說]] 記的限制：只有 4 席、單一缺陷、觀察性資料，且編碼者是提出假說的我（maker≠checker 沒閉合）。動 gate 之前必須先有一個為③設計的對照實驗。
