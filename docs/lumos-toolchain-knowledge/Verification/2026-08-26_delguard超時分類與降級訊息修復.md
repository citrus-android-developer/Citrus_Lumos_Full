# 2026-08-26_delguard超時分類與降級訊息修復

修 delguard 降級路徑的兩個缺陷。起因是[[Verification/2026-08-26_全repo術語統一為架構圖]]的過閘紀錄:該次兩筆 commit 的 pre-commit 都印 `delguard: 內部錯誤(TimeoutExpired),放行`,閘實際空轉,但輸出讀起來像雜訊。

## 缺陷

1. **超時被歸成 error**。`_delguard_confidence` 的 `git grep` 逾時拋 `subprocess.TimeoutExpired`,原本落進通用 `except Exception` → `--json` 給 `reason="error"`、文字印「內部錯誤(TimeoutExpired)」。這違反 `cmd_delguard_check` 自己 docstring 宣告的 `reason:"timeout"|"error"` 契約。
   ★這不是邊角★:`rem = max(0.1, deadline - elapsed)` 的下限保證了**預算耗盡時仍會餵一個過小的 timeout 給子程序**,所以這條路徑在大 diff 上是常態。
2. **降級輸出與正常通過難以區分**。兩者都不擋 commit,訊息是唯一區別;原文字「`delguard: 超時降級(2.0s),放行;本輪掃描不完整`」與「內部錯誤…放行」都像例行雜訊。

## 修法

- 新增 `except subprocess.TimeoutExpired` 專屬分支,置於通用 `except Exception` 之前 → `reason="timeout"`。
- 三處降級輸出(兩處 `_over()` + 兩個 except)一律加 `★本輪未實際守衛★`,並附「要完整掃描: `LUMOS_DELGUARD_DEADLINE=<秒>`」的自救指引。
- 測試鉤子沿用既有 `LUMOS_DELGUARD_RAISE`,值 `timeout` 走新路徑——不新增 env。

## 為何不調高預設 deadline

原本的判斷是「2.0s 太短,調高就好」。**量測後推翻**:完整掃描成本隨「被刪 token 數 × vault 規模」升——常見 token(如 JSONL 治理帳裡的 `commit`/`nodes`/`gate`)會讓 `_delguard_confidence` 的 `git grep` 輸出爆量,py 側再對每行逐一配 40 個 regex。2026-08-26 量測:**2 檔 / 63 刪除行**的 commit,完整掃描逾 5 分鐘未完成即中止。

pre-commit 需要即時回饋,沒有一個「既能跑完又不惹人厭」的值。所以本次**只修分類與訊息,不動預設值**——真解在降低掃描成本(v2 候選),留 `★DEBT★`。修完的差別是:閘一樣常常沒跑,但現在**看得出來它沒跑**。

## 驗證

1. **先紅後綠**:同樣三條斷言打在修復前的 `scripts/lumos` 上,得 `reason:"error"` 與無「未實際守衛」的舊文字;修復後轉為 `reason:"timeout"` 與新文字。
2. **五條路徑手動實跑**:`RAISE=timeout` 的 json/文字、`RAISE=1` 的 json/文字(須維持 `reason="error"`,不得被新分支吃掉)、`DEADLINE=0` 的文字。
