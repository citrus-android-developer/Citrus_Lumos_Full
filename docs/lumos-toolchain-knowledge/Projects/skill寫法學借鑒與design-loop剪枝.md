# skill 寫法學借鑒與 design-loop 剪枝

## 從哪來

外部 repo `mattpocock/skills`（2026-08-01 引入）。它的定位與 lumos 正交：**它強在「怎麼把一份 skill 寫得讓模型每次走同一條路」，lumos 強在「怎麼機械地證明它真的走了」。** 它整套沒有 canary、沒有收斂閘、沒有合約綁測試——靠寫得好的散文紀律。所以裁定是 **borrow-design 不是 adopt**：抄寫法學，不動驗證層。

## 借到的三樣東西

### ① 資訊階梯（本次直接用的）

skill 的內容排成一把梯子，依「模型多急著需要它」下降：

1. **步驟**——SKILL.md 裡的有序動作，主層。每步結束在一個**可檢查的完成判準**（模型分得出做完沒？），判準含糊會誘發**提前收工**。
2. **就地參考**——SKILL.md 裡的定義／規則／事實，按需查閱。
3. **外部參考**——推出 SKILL.md、放進同目錄的檔案，靠一個**指標**拉進來；★指標的措辭★（不是它指向誰）決定模型會不會、多可靠地去讀。

**lumos 的旁證**：`lumos-code-loop` 已經獨立長出這個結構（精實頭部 + `reference.md` + 一張「你正要做 X → Read reference.md 的哪一段」的表）。兩邊獨立收斂到同一個解，這是它可信的理由，也是本次直接套用的既有機制。

### ② 五個失效模式（當剪枝檢查表）

- **sediment（沉積）**——加東西感覺安全、刪東西感覺危險，於是陳舊的層一直堆著。**沒有剪枝紀律的 skill 的預設命運。**
- **sprawl（蔓延）**——就算每行都還有效、都不重複，太長本身就是問題。
- **no-op**——模型本來就會做的事，寫了等於付 token 說廢話。**測試：這句拿掉，行為會不一樣嗎？** 不會就刪**整句**，不要修辭。
- **duplication**——同一個意思出現在兩處。除了維護成本，還會**把那個意思在階梯上的排名灌水**。
- **negation**——用禁令引導會反效果（「別想大象」）。**對 lumos 只採一半**：lumos 的「嚴禁／不得」多屬硬護欄，他們自己也允許保留；採納的是「先試著能不能改寫成正面陳述」這個習慣，不是無差別改寫。

### ③ 硬依賴 vs 軟依賴（記著，本次不做）

他們用一條 ADR 把「skill 依賴 per-repo 設定」切兩類：**硬依賴**（沒設定就產出錯的東西）明寫 setup 指標；**軟依賴**（沒設定只是不夠銳利）只用模糊散文提，**不要把 setup 指標到處 cargo-cult**。

lumos 幾乎每支 skill 都在喊「先調用 `lumos-project-notes`」——按這個分法大多是軟依賴。這件事與剛交付的公開精簡版同源（給沒有完整工具鏈的人用＝軟依賴要優雅降級），值得另立題目。

## 本次動刀範圍

**只動 `lumos-design-loop`**（15,462 字元、單行最長 1,361 字，最痛的一支）。code-loop 已是目標結構、project-notes 已有 reference.md。

### ★硬不變量：不得遺失任何規則★

剪枝只准三種操作：

1. **壓縮措辭**（同一條規則講得更短）
2. **搬家**（SKILL.md → `reference.md`，並在原位留一個措辭夠強的指標）
3. **刪除純考古**——日期出處、工作包編號（`M1包`／`提效 M1`／`std F13`）、論文引用（arXiv 編號、會議名、作者）。★這些不是規則，是規則的來歷★；來歷屬於架構圖節點（本來就已經用 wikilink 連著），不屬於每輪都要載入的操作指令。

**不准**：刪規則、弱化判準、把「必須」改成「建議」。

> ⚠ **這條與本節點下方「五失效模式 · no-op」互相牴觸**（2026-08-13 自足性審計指出）：no-op 判準寫的是「這句拿掉，行為會不一樣嗎？不會就刪整句」——★字面上就是刪規則★。
>
> ★現況：拿 no-op 去刪一條紀律算不算違規，沒有任何一處說得出來。★ 兩條並存的處置掛在 [[Issues/散文紀律沒有退場機制]] 修法 B（待裁，兩選一：改寫成「量過沒差才准刪」納入窄門，或承認衝突並刪掉 no-op 判準）。
>
> 另請注意本節的**效力範圍**：這條不變量寫在「本次動刀範圍」底下，是為那一次剪枝作業（只動 `lumos-design-loop`）定的，**不是全 repo 常設規定**；全 repo 目前沒有任何關於散文紀律退場的常設規定。

### 驗證（maker≠checker）

- **機械清單 diff**：抽出改動前後的指令名、旗標、wikilink、★標記行、步驟編號，逐項比對。消失的每一項都要能指出「搬到 reference.md 哪裡」或「是考古、刻意刪」。
- **乾淨 agent 覆核**：把新舊兩份交給無脈絡 agent，只問一件事——**有沒有任何一條規則在新版裡不見了或變弱了**。

★合計變多是誠實的代價★：拆檔要付結構成本（標題、指標、出處對照表）。**買到的是「每輪固定載入的量」少了 28.5%**，而深規變成「撞到才讀」。這筆帳要照實講，不能只報 SKILL.md 那個數字。

### 驗證(maker≠checker,兩道)

**① 機械清單 diff**：指令名 9→9、旗標 25→25、wikilink 10→10，**零消失**。

**② 乾淨 opus agent 覆核**（只問一件事：有沒有規則不見了或變弱了）→ **PASS**。它逐條核了 30 個章節，並額外做了四項機械交叉驗證：

- **語氣詞計數**：必須 4→4、不得 9→9、一律 3→**4**、務必 1→**2**（兩處是**加強**）、建議 3→3、「盡量／可以」0→0。**無一條「必須」降級為「建議」。**
- **硬數字全數存活**：`cap=6`、`K=2`、`--need 2/3`、`panel_width 3/5`、`±20 行`、探針上限 2 次、`≲50 行`、每 5 個 caught 抽 1、light `cap=2`、delta `cap=3`、α 0.563、71.6%／83.3% …
- **合取條件沒被改成「或」**：D1 三條合取、D2 兩條合取、light K=1 四合取、gate 三錨全部維持 `∧`；`無 counts＝fail-closed`、`light 強制 fail-closed` 原封。
- **例外掃描**：新版所有「除非／例外／可跳／選配」逐條在舊版有對應，**未新增任何例外**。

它也專查了「日期是否承載語意」：`M0/M1` 標記移除處，語意由「目前靠你自核…別當它已自動擋」承接，**沒有被誤讀成「已自動擋」**；「自某日起改成 X」的三處規則本體全部保留在正文。

## 第二輪(2026-08-02):診斷迴圈先行

★先更正第一輪的分析★：我把外部 repo 當成一袋工具逐支評，但它其實是**一條有明確交接邊的流水線**——`ask-matt` 是一支專門回答「現在該用哪支」的路由 skill，交接邊上還寫死了「為什麼不能抄捷徑」（例：wayfinder 的地圖清楚後**交接在 `to-spec` 不是 `implement`**，直接接 implement 會把連結起來的細節丟掉）。而且我當時**只讀完 5 支就下結論**；41 支全讀完後排序整個變了。

**最有價值的不是 TDD 那支，是 `diagnosing-bugs` 的 Phase 1。**

它第一句就是「**這就是這支 skill 的全部，其他都是機械動作**」，然後給了一條硬完成判準：**一道你已經跑過至少一次的指令（貼出呼叫與輸出），red-capable／確定性／快／agent 可自行跑**；並明寫「如果你發現自己在這道指令存在之前就在讀程式碼建立理論——停」。

★缺口是真的★：`superpowers:systematic-debugging` 有「穩定重現」這個條目、也要求修法前先寫失敗測試，但**沒有完成判準**、沒有那道停止規則，而且 Phase 3 是「形成**單一**假說」（與 3-5 條排序假說相反）。lumos 自己只有 CLAUDE.md 的「未知行為實驗先行」一句，同樣沒有判準——**沒有判準的紀律，等於在你最急的時候不存在**。

★而我 2026-08-01 剛違反過它★：pre-push 假紅，我沒先拿失敗清單就跳去押 `GIT_DIR` 假說，而那份清單從第一分鐘就在 `/tmp/lumos-prepush-tests.log`。

**落地**：立 [[Systems/診斷迴圈先行]]；CLAUDE.md 與 `scripts/templates/graph-discipline.md` 的「實驗先行」那條**成對**加上完成判準一句 ＋ 指標（兩份由 doctor Check D 比對，已驗 0 漂移）。節點另收兩條 lumos 自己流血換來的規則：①「假說能重現出更嚴重的症狀，不代表它是眼前這個症狀的原因」（65 ≠ 3）②「為了驗證 X 會造成傷害，不得在真環境造成 X」（同日兩犯，各有事故節點）。

**沒做**：不新建 debug skill——PRIOR-ART ① 最小解在既有機制層，加判準 ＋ 一個 Systems 節點就夠，造新 skill 是多一個要維護的入口。

## 第三輪(2026-08-02):量測後裁定②④⑤不做

沿用第二輪學到的紀律——**先量測有沒有真的痛過，再決定要不要加規則**。三項逐一查證，結論是**都不做**，理由記在這裡，避免未來的人（或我）再提一次。

### ② expand–contract（大範圍重構的排序法）— ★不做：這個痛在 lumos 結構上不存在★

- 架構圖搜「大範圍重構／批次遷移／expand contract」→ **零命中**，沒有任何相關事故或計劃。
- 近 80 筆 commit 的最大爆炸半徑是 **18 個檔**，而且那些是「碼 ＋ 架構圖節點」成對變更，不是機械 rename 的扇出。
- 根本原因：**lumos 是單檔 CLI**（`scripts/lumos` 12,078 行）。外部那條規則描述的失效模式是「一個機械改動的爆炸半徑扇across 整個 codebase，一次編輯打爆上千個呼叫點、沒有任何垂直切片能落地是綠的」——**單檔專案沒有「上千個跨套件呼叫點」這回事**。

### ④ codebase-design 的兩把尺（刪除測試／一個 adapter vs 兩個）— ★不做：與承重約束直接衝突★

這兩把尺是用來決定**要不要引入接縫**的。但 lumos 的單檔形態**不是懶惰，是承重的**：

`scripts/slim-gen.py` 靠 `ast.parse(src_text)` 對**單一檔案**做可達性閉包 ＋ 行級手術，才生得出公開精簡版。把 `scripts/lumos` 拆成模組，等於要它改成跨模組 import 圖分析——**剛交付出去的那套生成機制會直接壞掉**。

把「多引入接縫」寫成 lumos 的設計指引，是把一條與承重約束衝突的建議放進架構圖，比不寫更糟。

### ⑤ seam 事先議定 — ★不做：既有對策已經接住過，不再疊第三個機制★

這一項**有一個真實資料點**：`Systems/測試假綠形態` 的第⑥型（根本沒去驗）——卸載器留下 manifest，2011 條測試沒有一條斷言過它該消失。事先議定測試邊界確實會逼出那條缺口。

但：

- 那次是**對打包後產物做端到端真跑**接住的，而那條對策**已經寫在第⑥型的「怎麼接住」裡**。
- `scripts/test_lumos.py`（14,983 行、2,069 條檢查）是**跟著 finding 反應式長出來**的——那個模型正是今天接住多數缺陷的東西，不是壞掉的東西。
- 只有一個資料點，卻要為它加第三套機制（事先宣告 → 確認 → 只准在議定邊界寫測試），**成本明顯大於證據**。

★對齊 design-loop 的 d4 裁定「前置加重一律拒」★：新守衛要有證據才加，不是有道理就加。

### 這一輪真正的產出

**不是三條新規則，是三個「查過、有證據、決定不做」的結案**——連同理由，讓這份清單不會變成永久掛著的未完成事項（那本身就是另一種沉積）。

★方法論★：第二輪靠數帳本找出真問題（cluster 帳 316:1），第三輪靠量測擋掉三個假問題。**同一條紀律，一次用來動手、一次用來不動手。**

### 已排序、尚未動的

**全部結案**：③ 已落地（見第二輪）；②④⑤ 量測後裁定不做（見第三輪，各附理由）。

★若日後情況改變才重開★：② 只有在 lumos 拆成多檔／多套件之後才有意義；④ 只有在單檔約束被解除（即不再用 AST 單檔閉包生成精簡版）之後才成立；⑤ 需要再累積 2-3 個「第⑥型」的真實逃逸才值得加機制。


## 誠實天花板

- 剪枝的收益（模型更可靠地走同一條路）**沒有機械量測**。本次不宣稱行為改善，只宣稱「規則沒少、字數變少、單行不再破千字」。真要驗，得拿 golden 語料做 replay 對照，那是另一個題目。
- 「沒遺失規則」靠清單 diff + 一個乾淨 agent，**不是證明**。清單抽取本身是「我枚舉了 N 種形態」——本專案已被這個坑咬過多次，故驗證推到覆核 agent 的語意判讀，不推在清單完備性上。
