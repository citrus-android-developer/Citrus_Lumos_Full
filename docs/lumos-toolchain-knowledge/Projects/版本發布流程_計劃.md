# 版本發布流程（計劃）

`PRIOR-ART:` ① **最小解在既有層**——`LUMOS_VERSION` 常數與 `_version_nudge()` 版本 nudge 已存在（`scripts/lumos:7080`，doctor Check N 呼叫），本案是「給它接上 git tag 與 CHANGELOG」，不是造新機制。② **世界解過**（真搜非印象，2026-07-29）：curl|bash 的釘版本／checksum 是熟坑，主流解法為「安裝腳本支援指定版本、預設抓 GitHub Release、附 checksum」（Sigstore「A Safer curl|bash」、Kusari「Pinning Dependencies」）；發版流程標準形態＝tag → CI 驗 → `gh release create` → CHANGELOG（GitHub Docs「Managing releases」、`gh release create`）。③ **裁定＝borrow-design**：照抄「tag＋Release＋CHANGELOG」形態，**不採**外部工具（release-it／goreleaser／semantic-release——零依賴家規，且它們解的是多語言打包發布，本專案沒有 build artifact）。自建部分只有膠水。

## 動機（r1 折入後的誠實版）

**使用者的真實需求（2026-07-30 澄清，此為本案定錨）**：「能夠對外版本更新、釋出我想釋出的版本、但只有我可以寫入。」

拆開就是三件事：對外能更新／放哪一版我說了算／只有我能寫。第三件在 public 個人 repo 上**天然成立**（預設即全世界唯讀、只有 owner 能寫），不需要任何設定。所以真正要解的是前兩件，而它們的本質是——**開發線與對外線要分開**。

`release` 分支正是這個分離：main 隨便推，release 只有你把它快轉過去。**壞掉的 main 傳不到任何人**，因為沒有人跟 main。

**r1 跨家族否決席的批評，這一版解掉了兩條、保留一條**：
- ✅ 「`get.sh` 腳本本身從 main 抓，壞 main 可讓它無視版本」→ **解掉**：README 的一鍵指令改指 `raw.githubusercontent.com/.../release/get.sh`。raw 可服務任意 ref，改一個字連第一段腳本都走對外線（tag 做不到這件事而不必每版改 README 網址）。
- ✅ 「釘 tag 破壞既有更新路徑」→ **解掉**：分支不是 detached HEAD。
- ⚠️ 「`latest` 是會移動的通道、不是可重現的 pin」→ **維持成立，且這是刻意的**。使用者要的就是通道（「釋出我想釋出的版本」＝我移動指標）。真正的 pin 是 opt-in `--ref <tag|sha>`。

**branch protection 的定位隨之改變**：從「本案的正解」降為「可選的縱深」——壞 main 已經傳不出去，required check 只再多保護 main 自身的整潔。仍留在 [[Projects/Codex外審吸收_計劃]] backlog ⑥。

**本案買到的**：
1. **釋出控制**：對外拿到什麼，由你移動 `release` 決定。
2. **發布溝通**：tag＋Release＋CHANGELOG 給出可指認、可回溯的版本身分。
3. **可回答「你在跑哪一版」**（[S8]）。

**明確不做**：semver 相容性承諾／多版本並存／降級支援／簽章與 SLSA provenance／自動 changelog 生成／**改變預設安裝行為**。

## 條款

### [S1] 版本單一源與一致性守衛
- 單一源＝`scripts/lumos` 的 `LUMOS_VERSION`（現值 `v1.0`），格式 `vMAJOR.MINOR`，不引入 patch 段與 semver 語意承諾。
- 新增 `t_version_single_source`：`LUMOS_VERSION` 必須與 `CHANGELOG.md` 最新一筆版本一致。
- **真值取得方式釘死**（r1：守衛的尺自己也會漂）：版本取 `^LUMOS_VERSION = "(v\d+\.\d+)"$` 單一定義點；CHANGELOG 取**第一個**符合 `[S2]` 釘死格式的標題。**兩邊任一解析不到＝紅燈，不得跳過。**

### [S2] CHANGELOG（格式釘死，不留猜測空間）
- 新增 `CHANGELOG.md`。標題格式**恰為** `## vMAJOR.MINOR — YYYY-MM-DD`（全形破折號，與 `LUMOS_VERSION` 同帶 `v` 前綴）。
- **不採 Keep a Changelog 的 `## [Unreleased]` 常駐區塊**（r1 折入）：常駐 Unreleased 會成為「最新一筆」，讓 `[S1]` 的解析在**每一次日常 push** 都撞「解析失敗即紅」。未發版的變更寫在 commit message 與架構圖，不進 CHANGELOG。
- 首筆＝`v1.0`，內容為「首次正式標記；此前為未標記的持續開發」，不回溯編造歷史。

### [S3] 發版動作（人執行，checklist）
0. **前置檢查**：`gh auth status` 已登入（r1 補：[S3] 第 3、5 步都依賴 `gh`，隱藏依賴要寫成步驟）。工作樹乾淨、在 `main`、與 remote 同步。
1. bump `LUMOS_VERSION` ＋ 寫 `CHANGELOG.md` 該筆 → commit → push。
   - **首次發版特例**（r1 補）：`LUMOS_VERSION` 已是 `v1.0`，此步只寫 CHANGELOG，無值可 bump。
2. **等 CI**：跑 `lumos ci-wait --json`，**必須確認 `verdict == "green"`**。
   - ★**不得只看 rc**★（r1 blocker 折入，兩席獨立指出）：`ci-wait` 的 rc0 涵蓋 `green`／`undetermined`／`timeout`／`no-run`／`unavailable`／`disabled` 六種判定中的五種——`gh` 未裝／未登入／網路斷會 fail-open 回 rc0（`scripts/lumos` 該路徑註解自書「fail-open,不擋任何流程」）。寫成 `lumos ci-wait && git tag ...` 這種最自然的寫法**會在 CI 根本沒被查到時放行發版**，而發版不可逆。
   - 非 `green` 一律停止，人工判斷後重來。
3. **移動對外線**：`git push origin main:release`（fast-forward；**不得 force**）。這一步才是「放出去」，後面兩步是留紀錄。
4. `git tag -a vX.Y -m "..."` → `git push origin vX.Y`。
   - **重跑清理**（r1 補）：若上次 tag 已建但 push 失敗，重跑前需 `git tag -d vX.Y`；若 release 已存在需先 `gh release delete`。
   - **既有 pre-push 行為預告**：對 tag ref，pre-push 會印 `非分支 ref、tier=high——advisory 放行(tag 內容 gate 另訂策略)`。**本計劃即為該 TODO 的定案處**：tag 內容 gate ＝ [S4] 的事後 workflow，pre-push 維持 advisory 不改（tag 指向的 commit 早已在 main 過完整閘）。
5. `gh release create vX.Y`，notes 取自該筆 CHANGELOG。
- 寫成 `RELEASING.md`（人看的 checklist），**不寫成腳本**——低頻、不可逆、需要人在場判斷。

### [S4] tag 閘（CI，事後檢查）
- **獨立 workflow 檔**（r1 定案）：不塞進 `ci.yml`。GitHub Actions 的 `on:` 是 workflow 層級，把 `tags:` 加進 `ci.yml` 會讓既有 job 在每次 tag push 重跑，且版本斷言 job 在一般 push 時無 tag 可比。
- **不重抄步驟**（r1 折入，本 repo 有清單漂移前科）：把 `ci.yml` 的驗證步驟抽成 **reusable workflow**（`workflow_call`），push 版與 tag 版都 `uses:` 它；tag 版額外加一步斷言 `LUMOS_VERSION == 該 tag 名`。若 reusable workflow 在實作時證實不可行，退路是加一條守衛測試比對兩份 YAML 的步驟清單——**不得靠人工同步兩份**。
- **限制誠實記**：事後檢查（tag 已存在才跑），讓錯誤可見，不能阻止 tag 被推出去。

### [S5] 對外通道＝`release` 分支（2026-07-30 設計轉向）
- **兩條線**：`main`＝開發線（可壞、CI 紅也無妨）；`release`＝對外線，**只有 owner 用 fast-forward 移動**。
- **發版動作**（併入 [S3]）：`git push origin main:release`。非 fast-forward 必須失敗而非 force（政策：只前滾）。
- **三個 clone 站一律預設 `release`**：`get.sh`、`cmd_bootstrap` 內建 clone（`scripts/lumos:7423`）、`get.ps1`。
  - **冷啟動 fallback**：`release` 分支尚不存在時 → 退回預設分支並印一行說明，不得炸掉。
  - 實作用 `git clone --branch release`（分支不是 tag，**不會進 detached HEAD**）。
- **README 一鍵指令改指對外線**：`raw.githubusercontent.com/<owner>/Lumos/release/get.sh`。這關掉 r1 否決席指出的「第一段腳本仍來自 main」缺口。
  - **限制**：GitHub raw 有 CDN 快取（數分鐘級），移動 `release` 後不是瞬間生效；發版後短時間內仍可能取到舊腳本。這是**延遲不是錯誤**，明記。
- **既有更新機制零改動**：消費端在**分支**上，`git pull` / `bootstrap --pull` / `lumos update` 全部照常，只是只會拉到 owner 批准過的內容。
- **維護者本機刻意留在 `main`**（吃前緣）；`git log release..main` 即「有哪些還沒放出去」。
- **真釘死＝opt-in**：`get.sh --ref <tag|branch|sha>`。
  - **旗標解析要改架構**（r1 補）：現行迴圈是純布林 token 比對（`case "$a" in --pull|--init)`），`--ref v1.2` 兩個 token 會雙雙落進 `*)` 被警告忽略。必須改成能消耗下一個 token。
  - **釘在 tag/sha ＝ detached HEAD，必須當場告知**：印明確警告「此安裝已釘在 `<ref>`，`git pull` 與 `lumos update` 不會拉到新版；要回到對外線請 `git -C <home> checkout release && git pull`」。
- **`--pull` 語意定案**：只對「在分支上」的 clone 有意義；偵測到 detached HEAD 時**印明確訊息並回非零**，不再靜默 WARN 後假裝成功（此為既有靜默失敗的修正，屬本案範圍）。

### [S6] notesmd 二進位 checksum
- `fetch-notesmd.sh` 已釘版本 `v0.3.6`，但無內容驗證（tag／release asset 上游可重傳）。
- **管線要拆**（r1 補）：現行是 `curl -fsSL "$URL" | tar xz -C "$TMP"` 直接串流，沒有落地檔可算指紋。必須改成「先存檔 → 驗 SHA256 → 再解壓」。
- **trap 要條件化**（r1 blocker 級細節，兩席指出＋自核）：現有 `trap 'rm -rf "$TMP"' EXIT`（`scripts/fetch-notesmd.sh:35`）無條件清除。若只加 `exit 1`，承諾的「保留暫存檔供人查」**不會發生且靜默不發生**。必須改為驗證失敗時清除 trap 或改用不受 trap 影響的保留路徑。
- **VER 被覆寫時的行為定案**（r1 補）：腳本支援 `fetch-notesmd.sh <版本>` 覆寫（既有升版測試流程）。指紋表**只涵蓋已釘版本**；覆寫成表外版本時 → **印明確警告「此版本無指紋、未驗證」並要求 `--allow-unverified` 才繼續**，否則中止。不靜默放行。
- 指紋來源＝當下實際下載到的檔案；**明記這是 TOFU（首次使用即信任），不是上游官方公布值**。
- 平台涵蓋 darwin_all / linux_amd64 / linux_arm64。

### [S7] Actions 釘 SHA
- `actions/checkout@v4` / `actions/setup-python@v5` 改完整 commit SHA ＋ 尾註原 tag。
- 代價：上游修補不會自動吃到，需人工升——列入 `RELEASING.md` 定期檢查項。

### [S8] `lumos --version`（r1 新增，補回動機二）
- 動機明列「可回答你在跑哪一版」，r0 卻只在隱患段寫「待審」，等於動機沒被實現。
- 新增 `lumos --version`：印 `LUMOS_VERSION` ＋ **來源 clone 的 commit sha 與 dirty 狀態**（vendored 副本沒有 git 脈絡時印 `(vendored, 無 git 脈絡)`）。
- **誠實**：這回答的是「這支 lumos 是哪一版」，不是「這台機器整體是哪一版」——見下方天花板。

## 實務隱患

- **一台機器可能同時有三個版本**（r1 補，Codex 指出＋自核）：全域 CLI（symlink→活 clone）、各專案 vendored 副本、**全域 Claude hooks**（`_install_hooks_py` → `_sync_global_claude(root)`，來源是「最後一個跑安裝的專案」的 vendored 副本，`scripts/lumos:7353`）。`[S8]` 的 `--version` 只能回答第一個。
- **`get.sh` 自身未釘**：釘的是它 clone 的內容，不是它自己。要連腳本都釘，使用者得改用釘版本的 raw URL——只能建議、不能強制。
- **tag 可變是事實**：`git tag` 可刪除、可 force-move，GitHub Release 可編輯。「只前滾不改寫」是**政策不是性質**，無機械強制。
- **`[S4]` 是事後閘**：錯的 tag 推出去後才紅，此時已可能有人裝到。
- **checksum 的信任根是 TOFU**：若首次下載時上游已被替換，指紋會把錯的東西鎖成「正確」。
- **`[S3]` 的存在性守衛本身會漂**（r1 承認）：要機械判定 `RELEASING.md`「列出全部步驟」，勢必硬編步驟關鍵字，checklist 改了守衛不會跟著改。**故降級為「檔案存在」即可，不假裝驗內容**——與其做一個會漂的假守衛，不如誠實只驗存在性。
