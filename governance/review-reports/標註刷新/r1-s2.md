# 標註刷新_計劃(r1) 謂詞邊界審查

逐一核對 spec 七個鏡頭項,對照 `governance/eval/build_goldset.py`、`retrieval_eval.py`、現有 `retrieval-goldset.json`、`retrieval-eval-history.jsonl`、`autonomous-loop.sh` 的實際行為。七項鏡頭全部命中,無一項可判「已查,無 finding」——逐條列出。

---

**Finding 1 [major] ——「候選池」三母體不一致,且未涵蓋緣起段自陳的失效母體**

> 引句：「重算每題候選池(`search_pool`/`edit_pool` 現成)」
> 引句：「hook 固定席噪音 77 條——新快照拉進 7/20 後全部未標節點,依「未標=噪音」規則淹沒指標」

問題:代碼裡實際存在三個不同母體——①出卷候選池(`build_goldset.py:42-54` search_pool 為 legacy top8∪ranked top8;`build_goldset.py:89-99` edit_pool 為 ranked top8+legacy top5+top5,再截斷到 12)、②考卷計分母體(`retrieval_eval.py:126-129` eval_search 的 legacy 完全不截斷、ranked 用 `--top 10`;`retrieval_eval.py:161-165` eval_edit 用 `impact --top 50`)、③hook 固定席(`retrieval_eval.py:172-198`,由 `impact` 動態判定 pinned,不受 `--top` 配額約束,且明文「固定席另計(安全機保,不算噪音)」不進 P@k/nDCG@k)。而緣起段自己指認的失效指標正是「固定席噪音」——S1/S3 的「候選池」定義(①)只是 search_pool/edit_pool 產生的小集合,spec 全文未交代它是否保證涵蓋②③,尤其未保證涵蓋動態判定、不受配額限制的固定席集合。若 S3 只對①做 `unjudged==0` 判定,無法保證②③無未標噪音——亦即無法保證不再重演本案動機事故。

查證:`governance/eval/build_goldset.py:42-54,89-99`;`governance/eval/retrieval_eval.py:126-129,161-198`

**Finding 2 [major] —— S1 diff 鍵為節點路徑字串,rename 後失效**

> 引句：「已標候選不重出(金標不重批);題目(queries)恆不變,動的只有語料側候選。」

問題:實測現有 `retrieval-goldset.json` 的 `labels` 鍵即節點檔案路徑(如 `"Projects/guard殺傷力驗證_計劃.md"`)。S1 的 diff 邏輯是「重算候選池與 labels 做集合差」,鍵若是路徑字串,節點一旦 rename(本 repo 架構圖紀律下常見),舊路徑的已標記錄變孤兒(永不清除)、新路徑會被判為全新未標候選,直接違反「已標候選不重出」的宣告,還會誤觸 S3 機械閘擋人。spec「刻意不做」段(line 54)只處理「content 改動→mtime 軟提醒」,完全未提路徑/rename 這個更根本的識別失效模式。

查證:`governance/eval/retrieval-goldset.json`(`labels` 鍵實測為路徑字串);spec r1-snapshot.md:37,54(對照缺口)

**Finding 3 [major] —— S3 的 rc1 與既有腳本 rc 慣例衝突**

> 引句：「重釘模式斷言:目標語料全題候選池 `unjudged == 0` 才寫入 `snapshot_commit`;否則 rc1 並吐 delta 清單(=「先跑 S1/S2」的機械提示)。」

問題:`retrieval_eval.py:356` 現有慣例是 `return 0 if ok else 1`——rc1 代表「分數閘 FAIL(調參訊號)」,且消費端 `autonomous-loop.sh:52` 明文寫死「完成判定看「gate 總判定」行,不看 rc——部分版本 gate FAIL 即回非零,那是調參訊號非執行失敗」,即 rc1 已被既有消費邏輯刻意忽略。S3 若沿用同一支腳本的 rc1 表達「必須先補標的硬擋」,會被同一套已建立的「rc1=軟訊號,別理」慣例吃掉,新閘對既有自動化消費端形同虛設;若改放在無 rc 慣例的 `build_goldset.py`,則同一子系統兩支腳本對 rc1 語意互斥,同樣是合約層級不一致。

查證:`governance/eval/retrieval_eval.py:274,295,356`(rc0/1/2 既有慣例);`governance/autonomous-loop.sh:52`(消費端明文不看 rc)

**Finding 4 [major] —— S4「top-K」與 10% 分母未定義,現況至少 4 種不同 K/母體並存**

> 引句：「`retrieval_eval.py` 每輪加印 unjudged rate(全題 top-K 候選中無標註佔比)並寫入 history jsonl 欄位。」
> 引句：「unjudged rate 超門檻(暫定 10%,實跑校準)」

問題:現有程式碼裡「K」至少有 4 種不同值/母體並存——search 主指標 nDCG@5(`retrieval_eval.py:110` k_search=5)、search legacy 不截斷、search ranked top10(line 128-129)、edit 預設 k=8(`-k` argparse default,line 271)但 impact 實際抓取母體是 `--top 50`(line 164)。spec「top-K」未指名是哪一個,「10% 的分母」也未定義是逐案例平均、全體候選數彙總、還是 search/edit 分開算、是否含 train split。字面照做,不同實作者會選出完全不同數字。

查證:`governance/eval/retrieval_eval.py:110-111,126-129,161-165,271`

**Finding 5 [major] —— 雙評審「一致」的精確定義未給,repo 內無既存合併邏輯可援引**

> 引句：「兩席一致 → 列入「建議 final」(免逐筆人裁);不一致 → 逐筆人裁(deep-read,沿用 `by`/`why` 欄位)。」

問題:判準是 0/1/2 三值(`governance/eval/raters/rater-instructions.md:5-7`),spec 未定義「一致」是否要求完全同值,1 vs 2 算不算一致;若判定為一致,`final` 該取哪一值也未講。搜過 `governance/eval/*.py` 與 `raters/` 目錄,目前沒有任何既存的雙評審合併/一致性判定程式碼可供沿用(`rater-claude.json`/`rater-codex.json` 只是原始標註輸出,無 merge 腳本),此為全新定義且未給值域,屬於「未定義詞」的必報例外。

查證:`governance/eval/raters/rater-instructions.md:1-11`;`governance/eval/raters/`(無 merge/consistency 腳本)

**Finding 6 [major] —— 過渡雙跑無法區分,corpus_revision_note 欄位位置與宣稱用途不符**

> 引句：「過渡:重釘當週新舊快照各跑一輪考卷,兩筆都進 history(重疊點,分數線可比);`corpus_revision_note` 記轉場與語料差異一句話。」

問題:實測 `retrieval-eval-history.jsonl` 每筆欄位為 `mode/ts/eval_head/knobs/vault_note/k/gates/pass/verdicts`,完全沒有 `snapshot_commit`/goldset 識別欄;`eval_head` 是「執行當下 repo 的 HEAD」(`retrieval_eval.py:347-348`),同一週兩次跑(新舊快照各一輪)會寫出同一個 `eval_head`,兩筆記錄無任何欄位可區分是用哪份 goldset(舊 285d429 或新快照)產生。而 `corpus_revision_note` 實際位置是 `retrieval-goldset.json` 頂層的單一字串欄位,描述的是「這份 goldset 檔案本身」的單一轉場敘述,不是 history.jsonl 的逐行欄位——結構上不可能拿它去標記 history 裡哪一筆對應哪個快照。消費端 `autonomous-loop.sh:36-47` 目前只用「最後一筆帶 ts 的 goldset 列」判斷是否該補跑,雙跑寫入後這個「取最後一筆」邏輯會直接吞掉其中一筆快照的分數,讀不出兩者的可比性。

查證:`governance/eval/retrieval-eval-history.jsonl`(尾端 5 筆實測欄位);`governance/eval/retrieval_eval.py:345-355`(history 寫入邏輯,無 snapshot 欄);`governance/eval/retrieval-goldset.json`(`corpus_revision_note` 為頂層單值);`governance/autonomous-loop.sh:36-47`(消費端取「最後一筆」邏輯)

**Finding 7 [major] —— edit 題目集透過即時 `git log` 生成,「題目恆不變」缺實作機制保證**

> 引句：「題目(queries)恆不變,動的只有語料側候選。」

問題:現況程式碼中,edit 題目清單唯一生成入口是 `edit_cases()`(`build_goldset.py:57-86`),依 `git log --no-merges -400`(相對「當前工作樹」HEAD 即時算)挑最近改動的前 20 個檔案——語料前進(HEAD 前移)時這份清單天生會漂(新 commit 觸及的檔案排進前 20,舊題可能被擠出)。spec S1 只說「重算每題候選池(`search_pool`/`edit_pool` 現成)」,未明講 delta 模式是否繞過 `edit_cases()`、改為僅對既有 `gs["edit"]` 陣列裡已存的 (file, delta, commit) 逐筆重跑 `edit_pool()`。若字面照做去重新呼叫既有唯一入口(即整個 `main()` 流程,含 `edit_cases()`),「題目恆不變」的宣告就不成立;即便刻意繞過 `edit_cases()`,`edit_pool(file, delta)`(line 89-99)也未處理 `file` 在語料前進後已被刪除/重新命名的情況(僅 `edit_cases()` 首次選檔時做過 `.exists()` 檢查,line 68),此邊界未在 spec 中被觸及。

查證:`governance/eval/build_goldset.py:57-86,89-99`(edit_cases 即時 git log;edit_pool 無存在性檢查)
