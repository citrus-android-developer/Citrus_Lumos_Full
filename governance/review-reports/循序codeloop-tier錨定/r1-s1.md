# 審計結果:循序codeloop-tier錨定 r1-snapshot.md(通才席)

### Finding 1(major):新增的反向守衛會靜默砍掉一個「目前其實能跑」的格式,且風險段完全沒提這個方向

實測:現行守衛只有 `eff_tier in (standard,high) and not panel_fmt → rc2` 與 `light and panel_fmt → rc2`,不管 kind、不管 standard∧panel_fmt=True 的情況——今天任何 kind 用 `--tier standard` 配 `--round` 都能成功記帳。真帳 `code側刪除傳播守衛`(7 筆、tier=standard、全帶 round、3 席含外家)是活例(雖被分類 indeterminate,守衛路徑同)。本案反向守衛把這條路堵死,但範圍刀明講「不動 design/standard」,實務隱患只討論「放寬錯格」方向,沒提同時在**收緊**一個目前合法的組合。

引句：「循序 legacy 格式=設計行為,放行;帳面反帶 --round(panel 格式)→ rc2 格式衝突(鏡像 light 的反向守衛)」
引句：「放寬一個 rc2 守衛的單一象限,最壞後果=放寬錯格讓 high/design 混進鬆判準」

### Finding 2(minor):審計修正紀錄段與 S2 本文對 tier_hint 描述不一致

審計修正紀錄總結說五分支點「均以 light-or-legacy 判樣式」,S2 本文卻標 tier_hint「維持 legacy-only,seq 不觸發」。真 code tier_hint 只判 legacy。兩句字面互斥。

引句：「均以 light-or-legacy 判樣式,單覆寫 width 兩條斷言必紅」
引句：「④tier_hint(**維持 legacy-only,seq 不觸發**)」

### Finding 3(minor):`_TIER_ROSTER` 表正上方那句舊註解沒排進修真範圍

scripts/lumos 的 `_TIER_ROSTER` 定義正上方寫死「code/standard(循序)v1 刻意不入表:既有 tier↔格式守衛使循序 code loop 無法錨定 standard(上游缺陷另案)」——S3 補列後這句當場變假話,但 S3 只提架構圖節點的 supersede,沒點名這行 code 註解。

引句：「[[Projects/派工編制資料化_計劃]] 範圍刀「不修 tier↔格式守衛」與「code/standard v1 不入表」段補 supersede 註記」

### Finding 4(minor):「走嚴」跟「fail-open」擺在一起講「方向一致」,措辭互斥易讀反

fail-open 慣例=失敗放行;此處實際要的是失敗擋(rc2)。照字面把守衛刻成「判不準就跳過不擋」會做出相反行為。

引句：「indeterminate(code 開頭無連字號)走嚴(=design 行),與 roster 的 fail-open 跳過方向一致」

### Finding 5(minor):disposal_cmd 列成獨立分支點,實際隨 rmode 自動跟動

disposal_cmd 的產生閘只看 tier(對 code∧standard 本就 True),模板直接內插 `{rmode}`——②修好後自動跟著不帶 --round,不需獨立接線。列成五點之一會讓實作者以為要單獨改。

引句：「③disposal_cmd 模板(seq→無 --round)」
