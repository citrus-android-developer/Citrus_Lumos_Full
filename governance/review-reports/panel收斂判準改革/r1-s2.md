# panel 收斂判準改革（A 案）r1-snapshot 證據面審查

白話總結：回放腳本本身可重算（我實跑過，輸出跟凍結檔逐字一致），四組回放比率（8/10、2/6、3/9、1/12）、右截尾 14、總帳 509 筆、code-slim-handoff 序列、RSNO 三輪皆 major、AEGIS 缺陷序列與 SPRT/capture-recapture 兩篇外部引文，全部核對過都對得上。但最關鍵的那組數字——「panel 直接層 n=4、右截尾 14」——背後的回放腳本對「乾淨輪」的定義，漏掉了現行 panel 閘三個條件裡的一個（capture-recapture 殘餘檢查）。我把腳本判準換成跟 `_loop_status_panel` 實際邏輯一致後重跑，發現這 18 筆（n=4＋右截尾14）裡有 11 筆（61%）其實在今天的真閘下根本不會判「輪有效通過」——也就是說，計劃拿來當內部主證的「K=1 收斂即停看不到後續」，有六成左右的樣本，現行系統本來就不會在那裡停。

## Finding 1（HIGH）——回放腳本 panel 層「乾淨輪」判準漏了 capture-recapture 殘餘檢查，n=4／右截尾14 兩個核心數字被系統性高估

- **file:line**：`governance/review-reports/panel收斂判準改革/r1-snapshot.md:20`
- **引句**：「①panel 直接層 n=4 觀測、反彈 1(code-relmainnet r2 乾淨→r3 major);右截尾 14≫4(K=1 收斂即停看不到後續)→★內部資料不足以獨立定案,方向與外部一致,且截尾方向=低估誤停率★」

**問題**：計劃 frontmatter 明寫 `DEP:scripts/lumos(_loop_status_panel / _round_valid_m2 兩函式)`（`r1-snapshot.md:26`），暗示回放腳本的「乾淨輪」判準就是在模擬這兩個真函式的行為。但讀 `governance/eval/k1_stop_replay.py:19-27`：

```python
def clean_round(rnds, mode):
    ...
    ca = sum(1 for r in recs if r.get("kind") == "caught")
    mi = sum(1 for r in recs if r.get("kind") == "missed")
    worst_bad = any(r.get("severity") in SEV_BAD for r in recs)
    return ca >= 2 and mi == 0 and not worst_bad
```

只驗了 `_loop_status_panel`（`scripts/lumos:3120` 起）三條合取裡的頭兩條（輪有效 caught≥2∧missed=0；存活 max≤minor），**完全沒碰第三條**——capture-recapture 殘餘檢查（`scripts/lumos:3151-3159`）：

```python
cc = next((r["capture_counts"] for r in latest if r.get("capture_counts")), None)
if cc is None:
    ... fails.append("無capture_counts")
else:
    remaining = _estimate_remaining_defects(cc)
    if remaining >= THRESH:  # THRESH=1.0
        ... fails.append("殘餘超門檻")
```

該條件 **fail-closed**：沒有 `capture_counts` 欄或估計殘餘 ≥1.0 都會讓真閘判 FAIL，不是「跳過」。這條在 canary-log 裡確實有資料可查（`capture_counts` 欄本來就存在每筆記錄）。

**實測**：我用 `_estimate_remaining_defects` 同款公式（`f1*(f1-1)/(2*(f2+1))`）重跑計劃引用的 `docs/.canary-log.jsonl` 與 landmark 兩份帳，把腳本判定「乾淨」的 panel 輪（n=4 clean_follow ＋ 14 右截尾，共 18 筆）逐筆補上第三條件：

| 分類 | 筆數 | 真閘會判「輪有效通過」 |
|---|---|---|
| n=4（clean_follow，有後續） | 4 | 僅 1 筆（`code-relmainnet r2`，`capture_counts=[1]`→殘餘 0.0） |
| 右截尾 14（無後續） | 14 | 僅 6 筆通過 |
| **合計** | **18** | **7（39%）**，11 筆（61%）用真閘會判「殘餘超門檻」或「無capture_counts」FAIL |

反例舉隅（腳本判「乾淨」但真閘會 FAIL）：
- `code-relmainnet r4-dref-delta`：`capture_counts=[1,1]` → 殘餘估計 1.0 ≥ 門檻，真閘判「殘餘超門檻」FAIL，並非收斂。
- `code-票券多筆帳 r1`（landmark）：`capture_counts=[3,2,1,1,1,1]` → 殘餘估計 3.0，真閘 FAIL。
- `code-recon-workbench r1`（landmark）：`capture_counts=[1,1,1]` → 殘餘估計 3.0，真閘 FAIL。
- `code-ops-fold r2`（landmark）：無 `capture_counts` 欄 → 真閘 fail-closed 直接 FAIL。

唯一真正「符合三條件、真閘會判通過」的 panel 反彈案例只有 `code-relmainnet r2→r3 major` 這一筆——巧合的是這正好是計劃唯一舉出的具名反彈案例（「反彈 1」），所以這一個案例本身站得住；但拿來撐住的分母（n=4、右截尾14）有六成不是真閘意義下的「K=1 收斂即停」，而是「今天的真閘本來就不會在這裡停」。計劃的措辭「K=1 收斂即停看不到後續」直接主張這些輪是「gate 會 PASS 並停下來」的實例，這個主張跟真函式行為不符。

**失敗場景**：design-loop 審查員若信任「n=4、右截尾14≫4」這組比例去校準候選設計的迫切度（例如判斷 (a)/(e) 該用多嚴的門檻），會把一個被腳本定義放寬帶來的「六成假陽性」誤當成「內部證據強度」的一部分——尤其計劃自己在同段寫「內部資料不足以獨立定案，方向與外部一致」暗示內部證據至少方向可信，但這個方向判斷的統計基礎（分子分母）本身有系統性偏誤，偏誤方向剛好是**誇大**現行系統的風險（回放腳本比真閘寬鬆，所以腳本判「乾淨」的案例中，有六成其實真閘不會放行——用這組數字去論證「panel 判準太鬆」，論證力比看起來弱很多，不是「不足以獨立定案」而已，是「這批樣本本身描述錯了現況」）。

## Finding 2（MEDIUM）——AEGIS 引文選擇性：只引非單調缺陷序列，未揭露同篇論文對計劃候選設計不利的兩條證據，且這兩條證據其實已經記在本專案自己的架構圖裡

- **file:line**：`governance/review-reports/panel收斂判準改革/r1-snapshot.md:19`
- **引句**：「★證據一(外部主證)★——AEGIS 迭代審計(arXiv 2605.12280,9 輪審 7152 行 spec):缺陷序列 15→8→12→2→8→1→4→1→0,★非單調收斂★——單乾淨輪後反彈兩次(2→8、1→4);「一輪乾淨=枯竭」在該實測誤停兩次」

**問題**：我對照 arXiv 2605.12280 摘要，「7152-line specification surface was audited across nine rounds...per-round counts of 15, 8, 12, 2, 8, 1, 4, 1, 0」——缺陷序列與「9 輪 7152 行」數字精確吻合，這條引用本身沒有寫過頭。

但查本專案架構圖 `docs/lumos-toolchain-knowledge/Systems/convergence-evidence-gate.md:16`，同一篇論文早就被記錄過，而且記了**另外兩條**與計劃當前候選設計直接相關、方向不利的證據：

> 「★同篇論文另外兩條直接證據★：嚴重度評審間一致度 κ=0.46 vs 分類 κ=0.80(支持「嚴重度不該單獨當閘」)；四家廠商 ×3 跑，★聯集才抓到全部 5 個種子缺陷★，而 Anthropic 那家嚴重度一致度最低(0.57)、誤報最高(1.33)——支持跨家族席，且★我們自己就是那一門★」

計劃引用同一篇論文卻只取「缺陷數序列非單調」這一段，沒有提到「嚴重度」這個維度本身在該論文裡評審間一致度很低（κ=0.46，遠低於分類任務的 0.80），而計劃現有候選設計裡至少 (a)(b)(c)(d) 全部建立在「severity 存活折入」或殘餘估計（同樣讀 severity/findings 欄）之上——這正是同一篇被引論文自己標記為弱訊號的維度。更直接的是：該論文测出「Anthropic 家族」審計員嚴重度一致度最低、誤報最高，而本專案的 canary 審計員本身就是這個家族（架構圖原句「我們自己就是那一門」）。這條對計劃「加嚴 severity-based 判準能治好誤停」的整體方向構成直接的反向證據，計劃卻完全沒有引用或處置，讀者若只看 r1-snapshot 這份計劃，會得到「AEGIS 論文全面支持本案方向」的印象，但同一篇論文其實也在質疑「拿 severity 當單一判準」這件事本身。

**失敗場景**：design-loop 審查員若只讀這份計劃、不主動去查 `convergence-evidence-gate.md`（該節點是計劃自己 `related` 列出的第一個節點，`r1-snapshot.md:10`），會誤判「AEGIS 這篇論文的證據力對本案候選設計毫無保留地支持」，漏掉一條本應被列入候選設計取捨（尤其是候選 (d) 存活折入數、候選 (c) capture-recapture 上界）風險評估的同源反證。

## Finding 3（LOW）——PRIOR-ART 引用 arXiv 2510.27106 支持「3-5 runs 平台期」的具體型態，但無法從論文摘要/可查內容核實這個細節

- **file:line**：`governance/review-reports/panel收斂判準改革/r1-snapshot.md:24`
- **引句**：「LLM 判官自我不一致 3-5 runs 平台期(arXiv 2510.27106 等)」

**問題**：查 arXiv 2510.27106（"Rating Roulette: Self-Inconsistency in LLM-As-A-Judge Frameworks"，Haldar & Hockenmaier，EMNLP 2025 Findings），論文主題確實是 LLM 判官跨次評分的低一致性（"low intra-rater reliability... almost arbitrary in the worst case"），大方向與計劃引用一致，論文存在、主題對得上，不是憑空捏造的引用。但無論是摘要或可查到的論文介紹，都沒有出現「3-5 runs」這個具體次數、或「平台期(plateau)」這個具體型態的措辭/數據——這個細節可能在論文全文的實驗章節裡（我沒有能力取得付費全文核對），也可能是計劃作者記憶/外推出的細節。由於這條引用只是 PRIOR-ART 背景陳述、不驅動任何候選設計的具體參數，即使該細節有誤，也不影響最終候選設計 (a)-(e) 的正確性，重要性遠低於 Finding 1/2。

**失敗場景**：design-loop 審查員或未來讀者若拿這句去核實「LLM 判官到底幾次評分會進入平台期」這個具體數字，會發現公開可查的論文摘要對不上這個細節，可能誤判整條 PRIOR-ART 搜索紀錄的可信度（殃及旁邊確實查證屬實的 AEGIS/SPRT/capture-recapture 三條引用）。
