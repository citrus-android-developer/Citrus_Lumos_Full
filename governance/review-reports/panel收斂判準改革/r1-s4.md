# panel 收斂判準改革（A 案）r1-snapshot 整合面審查

白話總結：這份 spec 列了五個候選判準（K=2、K=2+縮編、殘餘上界、衰減率、抽查輪），但**沒有一個候選對照過現有機械的三個硬約束**——tier=high 的 cap=3、`_loop_status_panel` 目前「只看最後一輪」的結構、以及 `--min-seats`/G3 只驗最後一輪的事實。文件裡還有一句自我引用「規則已定於某節末」但該節其實是空的（只指到一份純數據檔）。以下逐條列。

- **file:line**：`governance/review-reports/panel收斂判準改革/r1-snapshot.md:45`

**問題**：該段聲稱「抽查輪與 cap 的互動規則」已寫在文末〈回放輸出〉節。但實際核對 `r1-snapshot.md:48-50`〈回放輸出〉整節全文只有：

> 見 `governance/eval/k1-stop-replay-2026-08-05.txt`（腳本同目錄可重算）。

我進一步讀了該檔（`governance/eval/k1-stop-replay-2026-08-05.txt`，26 行）與同目錄的 `k1_stop_replay.py`（3171 bytes），兩者內容都是**回放統計輸出**（各 loop 的乾淨輪/反彈次數/右截尾計數），**完全沒有任何「抽中覆核輪不計入 cap」或「findings 照常走處置帳」的規則文字**。

## Finding 2（HIGH）——候選 (a)/(b) 的 K=2 與 tier=high 既有 cap=3 的相衝關係全文未提

- **file:line**：`governance/review-reports/panel收斂判準改革/r1-snapshot.md:24`
- **引句**：「①最小解在既有機制層——(a)/(b)只動 need 參數與席數表」

**問題**：查 `scripts/lumos:3880`：
```
_TIER_PARAMS = {"light": (1, 2), "standard": (3, 3), "high": (5, 3), "legacy": (1, 6)}  # tier→(width, cap)
```
panel 唯一實務路徑 tier=high 的 cap 是 **3 輪**（`cmd_loop_next` 在 `scripts/lumos:4068` `if rounds_count >= cap:` 判 cap-reached，優先序排在 converged 之後、之前無論如何都受這個 3 輪硬頂）。候選 (a)「K=2 連續有效乾淨輪」若不動 cap，在 cap=3 的預算內，唯一能收斂的排列只有「輪 1、2 皆乾淨」或「輪 1 髒、輪 2、3 皆乾淨（剛好卡在 cap 邊界）」——只要出現「乾淨→髒→乾淨」（非連續）這種本案自己列為主證的反彈模式（AEGIS 序列 2→8 之後又 1→4，K1_stop_replay 裡 `code-relmainnet @ r2` 就是「r1:blocker→r2:minor(乾淨/低)→r3:major」這種型態），loop 會**保證**撞 cap-reached、全部退化成人裁，而不是「更誠實地收斂」。PRIOR-ART 卻寫死「(a)/(b) 只動 need 參數與席數表」，隻字未提 cap 這個同一張表（`_TIER_PARAMS` 的第二個欄位）也可能要跟著動——若 cap 不動，K=2 對 tier=high 的實際效果很可能是「幾乎所有本案想抓住的反彈案例都直接判 cap-reached」，而不是文件宣稱的「更誠實地捕捉反彈」。

**失敗場景**：落地後把 `_round_valid_m2` 改成要求連續 2 輪，cap 表沒同步動——T8 這個本案自己在 `r1-snapshot.md:34` 舉的動機案例（「r1-r3 每輪都出 major、達 cap 攤人」）在新判準下同樣是 cap-reached 收場，新判準對這個動機案例本身沒有任何改善，只是把「一輪乾淨就誤放行」換成「幾乎必然 cap-reached 交人裁」，代價（人力）被完全略過未評估。

## Finding 3（HIGH）——`_loop_status_panel` 目前的核心結構是「只讀最後一輪」，K=2 需要的「跨輪比對」未被指出是結構性改動

- **file:line**：`governance/review-reports/panel收斂判準改革/r1-snapshot.md:26`
- **引句**：「DEP:scripts/lumos(_loop_status_panel / _round_valid_m2 兩函式)」

**問題**：`_loop_status_panel`（`scripts/lumos:3120`）與其 cluster 分支 `_loop_status_panel_clusters`（`scripts/lumos:3181`）目前都是：
```python
rid, latest = next(reversed(groups.items()))
```
——**只取最後一個 round group**，判準（三條合取 / 兩條合取）全部只作用在這一輪上。這正是 `skills/lumos-code-loop/SKILL.md:30` 自己講的：「`_loop_status_panel` 只取 `next(reversed(groups.items()))`，也就是★只看最後一輪★」。

候選 (a)/(b) 要求「連續 2 個有效乾淨輪」，這不是「調一個 need 參數」，而是要把「只看最後一輪」的核心資料流改成「看最後 2 個**有效**輪（要跳過中間的無效輪）」——且要決定：
1. cluster 帳的 ledger fold（`scripts/lumos:3192-3204`）目前是「所有有效輪」累積 fold，跟「只看最後 K 個有效輪」是兩種不同的聚合語意，兩者怎麼共存未定義；
2. 「連續」是指 round-id 連續、還是「有效輪」連續（中間夾無效輪算不算斷）——`_round_valid_m2` 本身只判單輪有效性，不含跨輪序列邏輯。

DEP 清單把這兩個函式並列，讀起來像「改這兩個既有函式內部邏輯即可」，但實際上是要新增一段目前不存在的「取最後 K 個有效輪」的選取/序列邏輯，且要決定它跟 cluster fold 的關係——這是結構性新增，不是參數調整，文件沒有指出這一層落差。

## Finding 4（MEDIUM）——候選 (b) 的「確認輪縮編」跟 `--min-seats`/`_TIER_PARAMS` 的單一寬度值衝突未提

- **file:line**：`governance/review-reports/panel收斂判準改革/r1-snapshot.md:22`
- **引句**：「(b) K=2+確認輪縮編(W=審計員席數,確認輪減半如 5→3,★材料全量★——反彈發生在同材料上,delta 確認確不了枯竭)」

**問題**：`_TIER_PARAMS["high"] = (5, 3)`——width 是**每個 tier 一個常數**，不是逐輪可變的。`cmd_loop_next` 的 `emit()`（`scripts/lumos:3972-3973`）把 `width`/`min_seats` 當成整個 loop 唯一值吐出：
```python
out = {"phase": phase, "tier": eff_tier, "round": n_next, "width": width,
       "min_seats": width, "cap": cap, ...}
```
`_panel_extra_checks`（`scripts/lumos:3032-3053`）收到的 `min_seats` 也是外部單一值傳入，逐輪一致地驗「這輪相異 auditor 數 ≥ min_seats」。候選 (b) 要「第一輪 W=5、確認輪 W=3」，等於要讓 min-seats 依輪次位置變動——這需要新的「輪位→width」對照表，而不是文件暗示的「席數表」小改（PRIOR-ART 同一句「(a)/(b)只動 need 參數與席數表」也把這條算進「最小解」，但沒說明這張表要從「tier→固定寬度」變成「tier×輪位→寬度」）。

## Finding 6（HIGH）——新判準對「進行中」loop 的回溯效力（review 要求 3：舊帳相容）未講清楚，且與架構圖裡已有的相反先例未對照

- **file:line**：`governance/review-reports/panel收斂判準改革/r1-snapshot.md:41`
- **引句**：「本 spec 必須過 design-loop 審（本節點正在做的事），且落地測試需含「舊帳在新判準下的回放對照」防靜默放寬」

**問題**：這句話講的是「拿舊帳回放來校準新判準的門檻」（一種驗證手段），**不是**「新判準上線那一刻，正在進行中、已經記了第 1 輪乾淨帳等著判收斂的 loop 該怎麼辦」這個問題。全文檢索「回溯」「進行中」「in-flight」等詞，`r1-snapshot.md` 只有這一處提到「回放對照」，且語境明確是驗證/校準用途，不是遷移政策聲明。

`_loop_status_panel` 是純函式、讀 `.canary-log.jsonl` 全量帳——一旦程式碼上線，**沒有版本旗標**，任何呼叫 `loop status --gate --panel` 的既有 loop 立刻吃新判準，包括那些在舊 K=1 規則下已經投入第 1 輪（可能審計員配置、輪次規劃都是照 K=1 預期做的）的進行中 loop。這跟本專案架構圖裡已經存在的相反先例正面衝突——`skills/lumos-design-loop/SKILL.md:13`：「design-loop 新 loop 一律走處置閘，**舊帳不回溯**」，design-loop 自己升級判準時明確選了「不回溯」這條路（新 loop 才吃新規則，舊 loop 照舊）。本案改的是同一類「閘自己」的判準，卻完全沒有對照這個既有先例、沒有說要不要比照辦理，這正是 CLAUDE.md 開場強調的「self-governance 特有」風險（本文件自己在同一段也點名了「裁判改自己的哨子」），但只處理了②③兩個風險點，沒處理「舊 loop 立即回溯生效」這個第三種風險。

**失敗場景**：一個 tier=high 的 code-loop 分支終審 loop，已經在舊規則預期下記了 round r1（乾淨），正準備呼叫 `loop status --gate --panel` 期待收斂；若在這之間新判準（K=2）上線，同一支指令突然要求 r2 也乾淨才過——而審計員與編排者對此毫無預警（SKILL.md 尚且還沒同步改，見 Finding 5），造成「規則變了但沒人被告知」的落差。

## Finding 7（LOW-MEDIUM）——候選 (e) 提到的 `probed` 欄位在既有 schema 中不存在、無落地路徑（未定義詞）

- **file:line**：`governance/review-reports/panel收斂判準改革/r1-snapshot.md:41`
- **引句**：「記帳只能記 `probed: true/false`」

**問題**：`scripts/lumos` 的 `canary record` 子命令（`cr.add_argument` 系列，`scripts/lumos:12219-12251`）是固定列舉欄位（`kind`/`auditor`/`token`/`note`/`loop`/`severity`/`findings`/`round`/`capture-counts`/`clusters`/`spec`/`reviewed`/`tokens`/`scope-lines`/`wallclock-min`/`tier`/`report`/`snapshot`/`findings-set`/`folded-set`/`accepted-set`/`accept-reasons`），**沒有 `--probed` 旗標，也沒有通用的「額外欄位」擴充機制**。文件把 `probed: true/false` 講得像是既有記帳能力的一部分（「只能記」暗示這是已有格式的限制），但這其實是一個全新欄位，需要新增 CLI 旗標與 JSONL schema 支援——這件事本身不難，但文件沒有標明它是「待新增」，容易讓 design-loop 審查員誤以為記帳機制已經支援、跳過對它的檢查。
