# 預註冊：進場路徑（context）vs 全文（show）的答題落差

> **在跑之前寫死**，跑完不得回頭改判準。沿本 repo 既有慣例（PPR 邊權消融的預註冊考卷）。
> 日期：2026-07-30 ｜ 來源動機：backlog ⑨（2026-07-30 治理日報引入，arXiv 2607.21962）

## 這不是論文複製，是適配（先講清楚）

論文（arXiv 2607.21962）比的是「人工摘要式記憶」vs「帶出處指針的架構圖記憶」，三週 vs 九週，
結論是排名反轉（摘要 96%→72%，帶出處升到 90%）。**本實驗不宣稱複製它**，理由三條：

1. **時間跨度不足**：本架構圖始於 2026-06-26，只有 5 週，做不了九週。改用「**節點被改寫幾次**」當軸——
   論文的機制是記憶被重寫／壓實的累積，改寫次數比日曆時間更貼。
2. **Lumos 的 summary 不是論文說的那種「摘要」**：它的 KEY 行**本來就帶出處指針**（`[test:]`、`[audit:]`、
   `[[wikilink]]`、日期、`scripts/lumos:7416` 這種座標）。按論文分類，它比較接近「會贏的那半」。
3. **實測發現 summary 不必然比 body 短**：38 篇 Systems 中 **34% 的 summary 比 body 長**，
   中位比值 0.60、範圍 0.25–2.46。所以「summary vs body」不是乾淨的壓縮對照。

## 真正要答的問題（對本專案有決策意義）

`lumos-project-notes` skill 規定的進場動作是「search → **context** → contracts」，
而 `lumos show`（讀全文）是 2026-07-21 才補進來、用來填「context 只給 summary 索引」的缺口。

> **照 skill 只跑進場三步的 agent，會不會答錯？答錯率跟節點被改寫幾次有沒有關係？**

## 兩組（真子集關係）

| 組 | 指令 | 是什麼 |
|---|---|---|
| **C（進場路徑）** | `lumos context <節點>` | skill 規定的進場動作所看到的全部 |
| **F（全文）** | `lumos show <節點>` | frontmatter ＋ body 全部，完整性上限 |

C ⊂ F（context 的內容都在 show 裡）。故 **F 不應低於 C**；若 F < C 即為雜訊指標。

## 樣本（機械選取，非挑選）

**選取規則（跑之前定，兩道機械條件）**：
1. **限 code-backed 節點**——該節點的主題必須實作在 `scripts/lumos` 或安裝腳本裡，否則出題者無從用程式碼建立獨立真值（純協議型節點如 `design-loop`、`risk-tiered-review` 因此排除）。
2. 在符合條件者中，按 `git log` 改寫次數取**最高 3 篇**與**最低 3 篇**。

結果：

- **高改寫**：`lumos-cli-read`(20)、`retrieval-ranking`(13)、`lumos-cli-lifecycle`(12)
- **低改寫**：`test-profile-multiplatform`(3)、`native-windows-support`(3)、`lumos-refcheck`(3)

> 註：初稿曾列 `design-loop`(21)、`risk-tiered-review`(3)，在**尚未出題、尚未看到任何結果前**因條件 1 換掉——
> 它們的真值只存在於協議散文裡，用它們出題等於拿文章考文章。此更動記錄於此，不得事後再動。

每節點 3 題 → **共 18 題**。

## 出題與計分（防循環論證）

- **出題者只讀程式碼／測試／git，不得讀架構圖節點**。每題須附 `file:line` 佐證的正確答案。
  （若出題者讀了節點再出題，就是拿文章考文章，兩組都會滿分。）
- **答題者只拿該組文字**，不得查任何檔案。答不出來必須寫「架構圖沒說」，不准猜。
- **三種計分結果**：`正確` / `錯誤`（自信答錯）/ `未答`（說架構圖沒說）。
  ★**「錯誤」比「未答」嚴重得多**★——論文的失效模式是**答錯**，不是承認不知道。

## 預註冊的預測

- **H1**：F ≥ C 的正確數。（C ⊂ F，若反過來就是雜訊）
- **H2**：C 的**錯誤率**在高改寫組 > 低改寫組。（腐化假說；若不成立＝我們的壓實層沒有腐化）
- **H3（本專案特有）**：C 的失敗多為「**未答**」而非「**錯誤**」。
  理由：summary KEY 行帶出處指針、且第一道機械探針（2026-07-30）顯示耐久層沒有靜默刪除。
  若 H3 成立，代表壓實層的問題是**覆蓋不足**（該去讀全文），不是**誤導**（給了錯答案）——
  這兩者的處置完全不同。

## 預註冊的判準（跑完不得改）

| 結果 | 結論 | 處置 |
|---|---|---|
| C 的**錯誤**（非未答）≥ 3/18 且高改寫組較多 | 壓實層會誤導 | 壓實規則要硬性保留出處指針；skill 進場三步要加「載重問題必讀全文」 |
| C 的錯誤 < 3/18，但**未答** ≥ 6/18 | 壓實層不誤導、但覆蓋不足 | 只改 skill 措辭（何時該升級到 `show`），不動壓實規則 |
| C 與 F 差距 ≤ 2 題 | 進場路徑目前夠用 | 不動；記負面結果 |

## 誠實天花板（先寫，防事後找補）

- **N=18，統計檢定力極差。** 只能看**大效果**（論文那種 96%→72% 的量級）。小效果測不出來，
  屆時的正確結論是「測不出來」，不是「沒有效果」。
- **出題者的選題偏好無法完全消除**：它讀程式碼出題，可能偏向程式碼裡顯眼、而架構圖本就不該記的細節。
  緩解＝要求題目限定在「該節點宣稱涵蓋的主題範圍內」。
- **單一評分者**：計分由一個 agent 做，未做第二判者覆核（成本考量，明記為缺口）。
- 本實驗**不**回答論文的原始問題（長期腐化），只回答「本專案進場路徑現在夠不夠」。

# 結果（2026-07-30 跑完，判準未回頭改）

## 原始計分

| 組 | 正確 | 錯誤 | 未答 |
|---|---:|---:|---:|
| **C（進場路徑 `context`）** | 12 | **1** | 5 |
| **F（全文 `show`）** | 15 | 1 | 2 |

## 預註冊假設的驗收

- **H1（F ≥ C）**：✅ 成立（15 ≥ 12），無雜訊指標。
- **H2（C 的錯誤集中在高改寫節點＝腐化假說）**：❌ **不成立**。C 唯一的錯誤出在
  `test-profile-multiplatform`——**改寫次數只有 3（低改寫組）**。
- **H3（C 的失敗多為「未答」而非「錯誤」）**：✅ **強成立**（5 未答 vs 1 錯誤）。

## 依「答題前分類」拆開看（本實驗真正的主軸）

| 類別 | C 正確/錯誤/未答 | F 正確/錯誤/未答 |
|---|---|---|
| **A 類（架構圖本就該記，11 題）** | **9 / 1 / 1** | **9 / 1 / 1** |
| B 類（實作細節，7 題） | 3 / 0 / 4 | 6 / 0 / 1 |

★**C 與 F 的 3 題落差，全部落在 B 類**★——也就是「架構圖本來就不該記」的實作常數
（`--top` 預設值、BM25F 權重、FENCE_RE 正則）。**在真正該記的 A 類上，兩組打平（9/1/1）。**

## 預註冊判準：三個band 都沒對上（如實記，不回頭改）

| 預註冊的 band | 實際 | 對上? |
|---|---|---|
| C 錯誤 ≥3 且高改寫較多 → 會誤導 | 錯誤=1，且那 1 個在低改寫 | ✗ |
| C 錯誤 <3 但未答 ≥6 → 覆蓋不足 | 錯誤=1 ✓，未答=5 | ✗（差 1 題） |
| C 與 F 差距 ≤2 → 目前夠用 | 差距=3 | ✗（差 1 題） |

**這是預註冊沒設好，不是結果曖昧。** 門檻挑在 5/6 與 2/3 的邊界上，落點剛好卡在縫裡。
正確處置是**照實記「落在band 之間」**，不是事後把門檻挪一格去湊一個乾淨結論。
下次設判準要避開整數邊界，或改用區間而非單點門檻。

## 唯一那個「自信答錯」值得單獨講（本實驗最有價值的產物）

**Q10：doctor 支援哪些測試 profile？**

- C 答：`6 種(android、backend、maestro、playwright、python、dart)` — **數量對，名字錯兩個**
- F 答：`csharp-xunit、kotlin-junit、maestro、playwright、python、dart` — 正確
- 真值（`scripts/lumos` TEST_PROFILES）：`csharp-xunit / kotlin-junit / maestro / playwright / dart / python`

**根因不是腐化，是壓縮時的概念疊合**：該節點 summary 的一行寫
「`[test:plat:name]` 平台前綴(**android/backend**/maestro/playwright)」——那是**平台前綴名**，
不是 profile 名；而真正的 `csharp-xunit`/`kotlin-junit` **只出現在 body**。
C 組於是把「平台名」當成「profile 名」拼出一份自信但錯誤的清單。

**這條的教訓比原本的腐化假說更實用**：
> 壓實層的風險不是「用久了忘記」，而是**把兩個相近但不同的概念壓進同一行，讀的人分不出來**。
> 而且它與改寫次數無關——這個節點只被改過 3 次，錯從一開始就在。

## 結論

1. **對本專案，「進場只跑 context 會不會答錯」的答案是：很少答錯，但會答不出來**——
   而答不出來的幾乎都是**本來就不該記在架構圖裡的實作常數**。
2. **腐化假說（H2）在本專案不成立**：唯一的錯誤來自低改寫節點，且機制是概念疊合而非時間衰減。
   這與同日的機械探針（Systems 層無靜默刪除）一致。
3. **真正該防的是「壓縮時把相近概念疊在一起」**，而不是「壓實會讓事實消失」。
4. N=18、單一評分者、五週歷史——**以上都只是方向性證據，不是決定級結論**。

# run 2（真實業務庫複驗，2026-07-30）：★結論是「我的實驗設計不夠格」★

在一個 **18 週歷史、改寫次數 66:1** 的真實消費端架構圖上重跑同一套（節點名與業務內容不外流，
完整紀錄留在該專案自己的 `governance/eval/`）。

## 表面數字（**不得引用**）

| 組 | 正確 | 錯誤 | 未答 |
|---|---:|---:|---:|
| C（`context`） | 6 | **0** | 12 |
| F（`show`） | 8 | **6** | 4 |

看起來是漂亮的反轉：「全文組自信答錯 6 題、壓實組零錯」。**逐條回查後，這個數字是假的。**

## 為什麼假：★我的真值自己有錯★

- **至少 1 題我的「正確答案」是錯的**——出題 agent 讀程式碼建立真值時**漏看了現行的關鍵檔案**，
  只讀到已標 DEPRECATED 的舊檔就下結論。F 的答案其實逐字對得上正確的那個檔。
- **另 2 題不該判錯**：一題 F 是「誠實說不知道＋附帶正確補充」，被計分規則吃成錯誤；
  一題 F 給的是 HTTP 狀態碼而非錯誤碼字串，兩者實際都真。
- **1 題的真值根本無法驗證**（要驗的物件其 DDL 不在可查範圍，出題者是**推論**不是查證）。

→ 真正站得住的錯誤大概只有 1–2 個。**原始計分表不可作為任何結論的依據。**

## 這一輪真正的產物（比原本要測的假設重要得多）

★ **我用「出題者只讀程式碼」來防循環論證，結果 oracle 自己錯了——因為沒有人檢查出題者。** ★

我設計了三段互不相見的分工（出題／答題／計分）來防 maker bias，
卻**唯獨沒給出題者任何檢查**：沒有第二出題者交叉驗、沒有要求它申報「查了哪些檔、可能漏了什麼」。
於是 oracle 一錯，下游的計分、A/B 分類、假設驗收全部連帶失效——**而表面上還是產出一張很好看的表。**

這正是本 repo 反覆講的那條：**驗證層的天花板是 oracle 品質**（見 memory:pbt-oracle-reliability）。
這次是它打在自己臉上：一個專門設計來測「知識層可不可信」的實驗，
自己的知識來源不可信，而且**差點就當成結論發出去了**。

## 仍然站得住的觀察（不依賴計分正確性）

- C 組自己說了 **12 次「架構圖沒說」**——這是 C 的原始輸出，與計分無關。
  壓實層對這批問題的**覆蓋明顯不足**。
- F 組幾乎每題都給得出實質內容——全文層資訊量遠高於壓實層。
- **兩輪、兩個庫、加上機械探針，都沒有出現「腐化」跡象**：
  C 的失敗型態一律是「沒有這條資訊」，不是「有但過時／錯亂」。
- 「F 比 C 更容易自信答錯」這個誘人的反轉——**本輪證據不足以支持，不寫成結論。**

## 對評測框架的硬性補丁（下次必做）

1. **出題者必須被交叉驗**：第二個獨立 agent 專門質疑「這題答案真的對嗎」，
   並**強制列出查過的檔案清單**。本輪只要有人問一句「還有沒有別的同類檔案」就能擋掉。
2. **真值分級**：`可機械查證`（單一檔案明文）vs `需跨檔推論`——後者**不得作為計分依據**，只能列為觀察。
3. **計分規則要能區分「誠實未答＋補充」與「自信答錯」**——本輪把前者吃成後者，製造了假訊號。
